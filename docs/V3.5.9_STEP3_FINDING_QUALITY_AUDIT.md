## 1. Failing Pytest Root Cause and Fix

### Root Cause

`test_auto_falls_back_to_openai` in `tests/unit/test_localization_service.py` failed because `Settings` with `_env_file=None` still reads from actual environment variables. The test didn't explicitly set `MIMO_API_KEY`, so when the real environment had `MIMO_API_KEY` set, Pydantic picked it up and auto-selected MiMo instead of falling back to OpenAI.

### Fix

Added `MIMO_API_KEY=""` to the `Settings` constructor in the test. Pydantic Settings v2 gives constructor values precedence over environment variables, so this explicitly overrides the env var.

### Verification

```
580 passed, 1 skipped (was 571 passed, 1 failed, 1 skipped)
```

## 2. Empty Agent Root Cause

### Benchmark Evidence

From Step 2.7 real MiMo benchmark:

| Speed Mode | ArchitectureAgent | CodeSmellAgent | MaintainabilityAgent | RefactorAgent |
|---|---|---|---|---|
| Balanced | 0 findings | 0 findings | 1 finding | 0 findings |
| Fast | 0 findings | 3 findings | 0 findings | 0 findings |

**3 of 4 agents returned empty findings in both speed modes.**

### Root Cause Analysis

The empty findings are NOT caused by:
- ❌ Validator rejecting valid medium/low findings (no severity filtering exists)
- ❌ Report composer hiding findings (no severity-based suppression)
- ❌ Bilingual schema causing parsing failures (display field is optional)
- ❌ Prompt saying "critical only" (it doesn't)

The most likely causes are:
1. **LLM returns empty `{"findings": []}`** — MiMo chose not to produce findings
2. **Prompt was too conservative** — "Avoid vague findings" guidance made the LLM overly cautious
3. **No minimum finding count specified** — prompt didn't encourage finding production
4. **Bilingual schema added cognitive load** — complex nested JSON schema made LLM return fewer findings

## 3. Raw/Parsed/Validated Finding Flow

### Pipeline (unchanged)

1. Evidence Retrieval → 2. Prompt Construction → 3. LLM Call → 4. JSON Parsing → 5. Evidence ID Filtering → 6. Validation → 7. Orchestrator Aggregation → 8. Deduplication

### Rejection Points

| Gate | Condition | Impact |
|---|---|---|
| Evidence empty | BM25 returns 0 records | Agent skips LLM entirely |
| JSON parse failure | Invalid JSON from LLM | Retry with error feedback |
| Missing evidence_ids | Finding has no evidence | Triggers retry |
| Evidence ID not in allowed set | Fabricated evidence reference | Finding dropped |
| Evidence ID not in store | Stale or invalid reference | Finding dropped |

### New Instrumentation

Added `finding_quality` log line per agent:
```
finding_quality agent=ArchitectureAgent raw=2 validated=1 dropped=1 no_findings_reason=none invalid_attempts=0 evidence_count=10
```

Added to `AgentExecutionState.metadata`:
- `no_findings_reason` — LLM's explanation when returning empty findings
- `validated_finding_count` — number of validated findings per agent

## 4. Prompt Changes

### Before
- Schema instruction only
- "Avoid vague findings" (too conservative)
- No finding count guidance
- No `no_findings_reason` field

### After
- Added explicit task: "Produce 1-3 actionable findings"
- Added: "Severity can be high, medium, or low — medium and low findings are welcome"
- Added: "If the evidence genuinely supports no findings, return an empty array with a reason"
- Added `no_findings_reason` field to JSON schema
- Simplified bilingual rules (removed redundant lines)
- Removed "Architecture findings should prefer production-code evidence" (too restrictive)
- Kept anti-hallucination instruction
- Kept quality guidance for concrete descriptions

### Key Prompt Addition
```
TASK: Analyze the evidence below and produce 1-3 actionable findings.
Each finding must be grounded in the provided evidence_ids.
Severity can be high, medium, or low — medium and low findings are welcome.
If the evidence genuinely supports no findings, return an empty array with a reason.
```

## 8. Step 4 Recommendation

Based on this audit, Step 4 should be:

**Option A: Real LLM validation of prompt changes** (RECOMMENDED)
- Run the same benchmark with the improved prompts
- Verify that more agents produce findings
- Measure if `no_findings_reason` provides useful diagnostics
- Cost: 1 MiMo benchmark run (~7 min)

**Option B: Prompt/output budget optimization**
- Simplify the bilingual schema to reduce cognitive load
- Consider splitting display generation from finding generation
- Reduce prompt token budget for faster responses

**Option C: 2-call grouped agents** (Track A from Step 2.7)
- Only if prompt changes don't improve finding quality
- Group: Architecture+CodeSmell, Maintainability+Refactor
- Expected: ~50% wall-clock reduction

**Not recommended for Step 4:**
- Single-call multi-agent (too complex for MVP)
- Chinese report productization (bilingual is already instant)
