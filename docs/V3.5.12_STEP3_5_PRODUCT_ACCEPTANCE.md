## 11. Bug Found During Acceptance

### Bug: `normalize_zh_text(None)` crashes when finding has no `caveat`

**Location:** `backend/reviewers/zh_quality.py:433`
**Trigger:** A bilingual finding with `caveat=None` causes `normalize_zh_text(None)` to be called from `reviews.py:430`.
**Impact:** API returns 500 error when fetching zh findings for a review where any finding lacks a `caveat` field.
**Status:** **FIXED** in this session — `normalize_zh_text` now accepts `str | None` and returns `None` unchanged.
**Test coverage gap:** All existing tests set `caveat` on every finding, so this was never triggered.

### Quality Issue: `ev_*` IDs not replaced in zh report body

**Location:** `backend/api/reviews.py:302-338` (bilingual zh export path)
**Detail:** The bilingual zh export path applies `render_localized_report` and `_render_bilingual_report` but does NOT apply `_display_map.replace_in_text()`. Raw `ev_*` IDs remain in the report body (e.g., `**Evidence:** \`ev_001\``). The en export path correctly applies this replacement.
**Impact:** zh exported Markdown shows raw evidence IDs in the report body instead of `[E1]`/`[E2]`.
**Severity:** Medium — evidence appendix correctly shows `## E1 · path:line`, but the report body references are not normalized.

### Quality Issue: Priority section uses English `first_step`/`impact` values

**Location:** `backend/reviewers/priority_layer.py:67-86`
**Detail:** `_why_important()` and `_suggested_first_action()` read `finding.impact` and `finding.first_step` (English values) instead of `finding._display_field("impact", "zh")` and `finding._display_field("first_step", "zh")`. The bilingual replacement step partially fixes this, but `normalize_zh_markdown` phrase replacements can create mixed English/Chinese text.
**Impact:** Priority section may contain English or mixed-language text for `first_step` and `impact` fields.
**Severity:** Low-Medium — most text is translated, but edge cases produce mixed output.
