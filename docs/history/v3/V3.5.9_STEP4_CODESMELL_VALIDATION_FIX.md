## 1. Root Cause of CodeSmellAgent Validation Failure

### Symptom
Benchmark from Step 3.5 showed:
- CodeSmellAgent: `raw=0, validated=0, invalid_attempts=2`
- Other agents: ArchitectureAgent (2 findings), MaintainabilityAgent (2), RefactorAgent (3)

### Root Cause
`_parse_findings()` failed on **both** LLM attempts. Two contributing factors:

1. **Markdown code fences**: The LLM (MiMo) wrapped JSON output in ` ```json ... ``` ` fences. Python's `json.loads()` fails on fenced strings. This affected all agents but CodeSmellAgent was most vulnerable because its evidence is more abstract (code quality patterns vs. concrete architecture/refactor patterns).

2. **Prompt lacked concrete JSON example**: The prompt described the schema in prose but provided no example. Smaller LLMs (like MiMo) need explicit examples to reliably produce structured output. The other agents happened to succeed because their evidence was more concrete, giving the LLM stronger grounding.

### Why CodeSmellAgent Specifically Failed
CodeSmellAgent's evidence query (`"complexity duplicate long function too many calls code smell hotspot"`) retrieves abstract quality patterns. Without a concrete example in the prompt, the LLM struggled more to produce valid structured JSON for code quality findings than for architecture or refactoring findings.

---

## 2. Exact Parser/Validator/Prompt Issue

### Parser Issue (`backend/llm/structured.py`)
`_parse_findings()` called `json.loads(completion)` directly on raw LLM output. If the LLM wrapped JSON in markdown fences, parsing failed immediately.

### Prompt Issue (`backend/agents/evidence_agent.py`)
The `_render_prompt()` method:
- Described the schema as a single-line JSON template (hard to parse visually)
- Provided no concrete example of a valid finding
- Did not explicitly instruct "no markdown fences"

### Validator Issue
No validator issue. `FindingValidator` was working correctly — it never received any findings because they were all dropped at the parse stage.

---

## 3. Fix Applied

### 3a. Code Fence Stripping (`backend/llm/structured.py`)
Added `_strip_code_fences()` static method that strips ` ```json ... ``` ` and ` ``` ... ``` ` wrappers before JSON parsing. Called at the start of `_parse_findings()`.

```python
@staticmethod
def _strip_code_fences(completion: str) -> str:
    stripped = completion.strip()
    match = re.match(r"^```(?:json)?\s*\n?(.*?)\n?\s*```$", stripped, re.DOTALL)
    if match:
        return match.group(1).strip()
    return stripped
```

### 3b. Diagnostic Logging (`backend/llm/structured.py`)
Added parse failure logging in `generate_findings()` that records:
- Attempt number
- Error type (JSONDecodeError, ValidationError, etc.)
- Completion length
- Sanitized error message (first 200 chars)

No full LLM response or prompt is logged.

### 3c. Prompt Improvement (`backend/agents/evidence_agent.py`)
Updated `_render_prompt()` with:
- Explicit instruction: "Return ONLY valid JSON. No markdown fences, no explanation text."
- Structured list of required fields with types and constraints
- Compact example showing a complete valid finding with bilingual display
- Category field uses agent's actual `self.category` (not hardcoded)

## 4. Timing Attribution Result

### Problem
Step 3.5 benchmark showed:
- `report_compose = 439,909ms`
- `total_pipeline = 444,619ms`

This was misleading because `report_compose` in `report_generator.py` wrapped the **entire** `generate()` method, including all agent orchestration (LLM calls). The 439,909ms was ~99% agent LLM time, not report composition.

### Root Cause
In `report_generator.py`, `compose_started` was captured at the top of `generate()`, and `compose_duration_ms` was computed at the bottom. This measured everything: agent orchestration + report composition + diff scope append.

---

## 5. Timing Attribution Fix

### Changes

**`backend/reviewers/report_generator.py`:**
- Split timing into two stages:
  - `agent_orchestration`: time from `generate()` entry to just before compose step (includes all agent LLM calls)
  - `report_compose`: time for the actual compose step (diff scope append only)

**`scripts/benchmark_real_review.py`:**
- Added `agent_orchestration` to the pipeline stages display list

### Expected Result
After fix, benchmark timing should show:
- `agent_orchestration ≈ 439,900ms` (agent LLM calls)
- `report_compose ≈ 5ms` (diff scope append + file write)
- `report_render ≈ 439,910ms` (total report generation)
- `total_pipeline ≈ 444,619ms` (full pipeline)

## 7. Remaining Risks

1. **LLM may still produce invalid JSON**: Code fence stripping helps, but the LLM might return other malformed structures. The retry mechanism handles this (max_retries=1 gives 2 attempts total).

2. **Category mismatch**: The prompt now instructs `category: "code_smell"` but the LLM might return variations ("Code Smell", "code_smells"). The Pydantic schema accepts any string, so this won't cause parse failures, but the validator doesn't enforce category-section matching.

3. **Evidence quality**: If the evidence retriever doesn't find code-quality-relevant evidence for CodeSmellAgent, the agent will correctly return no findings. This is by design, not a bug.

4. **Timing overhead**: The code fence stripping regex runs on every parse attempt, adding negligible overhead.
