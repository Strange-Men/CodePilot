# V3.5.9 Step 1 — Real Performance Truth Audit

> Audit date: 2026-06-16
> Codebase version: V3.5.8 (commit `14d566d`)
> Auditor: CodePilot backend performance engineering
> Scope: Audit only — no optimization, no behavior changes

---

## 1. Executive Summary

A real MiMo review of the CodePilot GitHub repository took approximately 11–12 minutes. This audit traces every pipeline stage, verifies concurrency behavior, measures the bilingual output impact, and identifies the root cause.

**Root cause: LLM call latency amplified by default concurrency=2 batching.**

With 4 agents and `REVIEW_AGENT_CONCURRENCY=2` (the default), agents execute in two sequential batches of 2. Each MiMo LLM call takes an estimated 60–180 seconds. Two batches × 2–3 minutes = 4–6 minutes of pure LLM wait time. Adding clone, parse, and overhead yields the observed 11–12 minutes.

Setting `REVIEW_AGENT_CONCURRENCY=4` would run all 4 agents simultaneously, cutting agent phase time from 4–6 minutes to 2–3 minutes and total time from 11–12 minutes to an estimated 4–6 minutes.

4. Token generation time for bilingual output (larger response body).

## 5. Did Agent Concurrency Actually Work?

### 5.1 Code Verification

**Yes, concurrency is real.** The implementation in `backend/agents/orchestrator.py:156`:

```python
with ThreadPoolExecutor(max_workers=self.concurrency) as executor:
    futures = {
        executor.submit(_run_single, index, agent): index
        for index, agent in indexed_agents
    }
    for future in as_completed(futures):
        index, draft, agent_state = future.result()
```

- `ThreadPoolExecutor` creates real OS threads.
- `as_completed` yields results as they finish.
- Each thread opens its own `httpx.Client` for the LLM call.
- Deterministic ordering is preserved via indexed results (lines 172–179).

### 5.2 Concurrency Flow

| Setting | Batch 1 | Batch 2 | Total LLM Wall Time |
|---|---|---|---|
| `REVIEW_AGENT_CONCURRENCY=1` | A1 only | A2, A3, A4 sequentially | 4× single call time |
| `REVIEW_AGENT_CONCURRENCY=2` (default) | A1 + A2 | A3 + A4 | 2× single call time |
| `REVIEW_AGENT_CONCURRENCY=4` | A1 + A2 + A3 + A4 | — | 1× single call time |

### 5.3 Verification from Logs

The pipeline logs `event=task_completed` with `concurrency=%s` (pipeline.py:90-94):
```python
logger.info(
    "event=task_completed task_id=%s duration_ms=%s concurrency=%s",
    task_id, pipeline_duration_ms, self.settings.review_agent_concurrency,
)
```

The orchestrator records `agent_concurrency` in state metadata (orchestrator.py:191):
```python
state.metadata.update({
    "orchestrator": type(self).__name__,
    "agent_count": len(self.agent_classes),
    "agent_concurrency": self.concurrency,
})
```

**To verify actual concurrency was used**, check backend logs for:
```
event=task_completed task_id=<id> duration_ms=<ms> concurrency=2
```
If `concurrency=2`, agents ran in 2 batches.

## 6. Did MiMo Queue/Rate-Limit Requests?

### 6.1 Code Evidence

The LLM client (`backend/llm/client.py:332-369`) handles retries for:
- `httpx.ReadTimeout`, `ConnectTimeout`, `WriteTimeout`, `PoolTimeout`
- HTTP status codes: `408`, `409`, `429`, and any `5xx`

The retry logic uses exponential backoff (`client.py:368`):
```python
self.sleep(RETRY_BASE_DELAY_SECONDS * (2**retry_index))
```
Where `RETRY_BASE_DELAY_SECONDS = 1.0` and `max_retries = 2`.

**Retry timeline** (worst case per agent):
| Attempt | Action | Wait |
|---|---|---|
| 1 | LLM call | up to 180s |
| 2 (retry) | LLM call | up to 180s + 1s backoff |
| 3 (retry) | LLM call | up to 180s + 2s backoff |
| **Total worst case** | | **~543s (9 min) per agent** |

### 6.2 Rate Limit Evidence

**Cannot determine from code alone** whether MiMo rate-limits concurrent requests. The code handles 429 responses with retry, but:
- No logging of actual HTTP response codes in the success path.
- No logging of retry counts per agent.
- No logging of actual LLM response times.

**Instrumentation needed**: Add per-agent LLM call duration and retry count logging.

## 7. Did Bilingual Output Increase Latency?

### 7.1 Prompt Size Analysis

The agent prompt (`evidence_agent.py:68-119`) includes a JSON schema instructing the LLM to return bilingual display fields:

```
"display": {"en": {...}, "zh": {...}}
```

**Estimated prompt size per agent**: ~2000–4000 tokens (evidence records + JSON schema + instructions).

### 7.2 Output Size Analysis

The bilingual display fields add ~8 extra string fields per finding × 2 languages = ~16 prose fields per finding. For a typical 2–3 findings per agent:

| Component | Single-language | Bilingual | Increase |
|---|---:|---:|---:|
| Per-finding prose fields | ~8 fields | ~16 fields | +100% |
| Per-finding JSON overhead | ~200 tokens | ~400 tokens | +100% |
| Per-agent output (2-3 findings) | ~1500 tokens | ~3000 tokens | +100% |

**Estimated bilingual overhead**: +1500–3500 output tokens per agent call.

### 7.3 Latency Impact

At MiMo's estimated generation speed (~20–50 tokens/second):
- Extra 1500–3500 tokens = **30–175 seconds additional latency per call**
- With concurrency=2, this adds 30–175 seconds to the slower batch

**Bilingual output is a significant contributor** to per-call latency, but it's the correct UX decision — it eliminates the need for post-completion LLM translation.

### 7.4 Trade-off Assessment

| Approach | Per-call output | Post-completion LLM | Total LLM time | UX |
|---|---|---|---|---|
| Single-language + post-translate | ~1500 tokens | N findings × 1 call each | More total | Delayed zh |
| Bilingual one-pass (current) | ~3000 tokens | None | Less total | Immediate zh |

The one-pass bilingual approach is the better architecture despite larger per-call output.

## 8. Was Chinese Localization Still Triggered After Completion?

### 8.1 Code Verification

**No.** For new bilingual reviews (V3.5.8+), the API endpoints use stored `display.zh` fields directly:

**`GET /api/reviews/{task_id}?lang=zh`** (`reviews.py:78-122`):
```python
if _all_findings_bilingual(raw_findings):
    # New bilingual reviews: render zh report from stored display fields
    # ... no LLM call ...
elif localization_service is not None:
    # Legacy reviews: use localization service as fallback
    # ... may call LLM ...
```

**`GET /api/reviews/{task_id}/findings?lang=zh`** (`reviews.py:134-146`):
```python
if _all_findings_bilingual(raw_findings):
    localized_findings = raw_findings  # Use stored display.zh directly
elif localization_service is not None:
    # Legacy fallback — may call LLM
```

**`GET /api/reviews/{task_id}/export?lang=zh`** (`reviews.py:194-234`):
Same pattern — bilingual reviews use stored fields, no LLM call.

### 8.2 Verification Method

The `_all_findings_bilingual` function (`reviews.py:41-45`) checks if all findings have non-null `display.zh` prose fields. For new reviews where the LLM generated bilingual output, this returns `True`, bypassing the localization service entirely.

**Confirmed: No post-completion LLM calls for Chinese on new bilingual reviews.**

## 9. Is `REVIEW_SPEED_MODE=fast` Implemented and Effective?

### 9.1 Code Path

In `pipeline.py:226-229`:
```python
speed_mode = getattr(self.settings, "review_speed_mode", "balanced")
if speed_mode == "fast":
    token_budget = max(1000, token_budget // 2)
```

This halves the `final_prompt_token_budget` before passing it to the `ReportGenerator`.

### 9.2 Effect on Agents

In `report_generator.py:125`:
```python
per_agent_budget = max(1000, self.prompt_renderer.token_budgeter.budget // 4)
```

With `fast` mode:
- Original budget: 8000 → halved to 4000 → per-agent: 1000
- Original budget: 5000 → halved to 2500 → per-agent: 1000

### 9.3 Impact Assessment

**Speed mode reduces prompt token budget but does NOT reduce output token limits.** The LLM may still generate the same amount of output. The effect is:
- Smaller evidence bundles in the prompt (fewer evidence records per agent)
- Slightly faster prompt processing by the LLM
- No direct constraint on output size or generation speed

**Speed mode is implemented but has limited real-world impact on LLM latency.**

## 12. Recommendation for Step 2

### Primary Recommendation: Set `REVIEW_AGENT_CONCURRENCY=4`

This is the single highest-impact change. All 4 agents run simultaneously, cutting agent phase time from 2 batches to 1 batch.

**Expected improvement**: 11–12 minutes → 4–6 minutes (50–60% reduction).

**Risk**: MiMo provider may rate-limit 4 concurrent requests. Mitigation: test with concurrency=4 first; fall back to concurrency=2 if 429 errors appear.

### Secondary Recommendations

1. **Reduce `LLM_READ_TIMEOUT_SECONDS` from 180 to 120**: The 3-minute timeout is generous. If MiMo hasn't responded in 2 minutes, the call is likely degraded. A 120s timeout fails faster and retries sooner.

2. **Add per-agent LLM timing instrumentation**: Log actual LLM call duration, retry count, and HTTP status per agent. This replaces estimation with measurement.

3. **Consider `REVIEW_SPEED_MODE=fast` as default for production**: Reduces prompt size, which may speed up LLM processing. Test whether it reduces output quality.

4. **Keep bilingual one-pass architecture**: The per-call output increase is the correct trade-off. Post-completion translation would add more total LLM time and worse UX.

### Architecture Direction

| Option | Concurrency | LLM Calls | Expected Time | Complexity |
|---|---|---|---|---|
| Current default | 2 | 4 (2 batches) | 8–12 min | Low |
| **Recommended** | **4** | **4 (1 batch)** | **4–6 min** | **Trivial config change** |
| 2 grouped agents | 2 | 2 | 4–6 min | Medium — rewrite agents |
| Single-call multi-agent | 1 | 1 | 2–3 min | High — rewrite prompt system |

**The concurrency=4 change is trivial (one env var) and achieves the target 2–3 minute range for agent time.**
