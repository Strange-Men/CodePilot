# V3.7 Step 1.1 — Hard Fix Chinese Leakage Gate

## Why Step 1 Failed

V3.7 Step 1 introduced a centralized Chinese presentation pipeline (`zh_presentation.py`) with English leakage detection. However, Chinese reports still contained mixed Chinese+English sentences because the detector had a critical blind spot:

**Root cause**: `is_english_leakage()` returned `False` immediately if the text contained ANY Chinese character. Similarly, `detect_english_natural_language_leak()` in `zh_quality.py` only flagged lines with `chinese_chars == 0`. This meant mixed Chinese+English prose passed through completely undetected.

### Failing examples from V3.7 Step 1

```
❌ "以下证据指出 a repository concern that should be reviewed before changing 入口文件"
❌ "shared dependencies, or refactoring boundaries"
❌ "If this boundary is part of a 公共 API, changing it may break downstream consumers."
❌ "The selected evidence highlights"
```

These mixed sentences appeared in rendered zh reports because:
1. The field-level detector (`is_english_leakage`) skipped any text with Chinese chars
2. The metadata-level detector (`detect_english_natural_language_leak`) skipped lines with Chinese chars
3. The metadata repair (`repair_zh_metadata`) did partial replacements that left English residue

## Mixed Chinese+English Detection Rule

The fix adds a two-path detection strategy:

### Path 1: Pure English (existing)
If text has NO Chinese characters, check if it's a code symbol, path, command, tech name, or evidence ref. If not, flag as leakage.

### Path 2: Mixed Chinese+English (new)
If text HAS Chinese characters, strip all "allowed" English tokens (tech names, code symbols, paths, evidence refs, inline code), then check if 3+ consecutive common English words remain. If so, flag as leakage.

**Allowed English in zh reports** (not flagged):
- File paths: `src/flask/app.py`
- Code symbols: `send_static_file`, `OpenAICompatibleClient`
- Commands: `pytest tests/test_cli.py`
- Tech/API terms: Python, Flask, HTTP, JSON, CLI, API, SQL, DB, UI, OpenAI, MiMo
- Evidence refs: `[E1]`, `[E2]`
- Code blocks and inline code

**Disallowed English** (flagged even when mixed with Chinese):
- 3+ consecutive common English words
- English function-word chains: "that should be", "before changing", "if this"
- English clauses after Chinese prefixes
- English sentences inside prose fields

## Final Markdown Gate

New function: `assert_no_english_natural_language_zh(markdown: str) -> list[str]`

This is the safety net for future regressions. It:
1. Strips fenced code blocks
2. Strips inline code
3. For each non-code line, checks for English prose using the mixed-text detector
4. Returns a list of leaked fragments (empty = clean)

Use in tests:
```python
from backend.reviewers.zh_presentation import assert_no_english_natural_language_zh

def test_zh_report_clean():
    report = generate_zh_report()
    leaks = assert_no_english_natural_language_zh(report)
    assert leaks == [], f"English leakage found: {leaks}"
```

## Limitations

1. **Word-list dependent**: Detection relies on `_COMMON_ENGLISH_WORDS` (~250 words). Uncommon English words not in this list won't be counted toward the consecutive threshold. This is acceptable because 3+ consecutive common words is a strong signal.

2. **Threshold sensitivity**: The 3-word consecutive threshold may miss very short English clauses (2 words) or flag unusual but valid Chinese+English patterns. False negatives are preferred over false positives for short fragments.

3. **Code symbol edge cases**: Plain lowercase words like "changing" or "running" that are not in `_COMMON_ENGLISH_WORDS` are treated as potential code symbols and preserved. This is correct for detection (they reset the consecutive counter) but means some verb forms slip through.

4. **No LLM translation**: The repair uses templates, not dynamic translation. Repaired fields get generic Chinese text based on category, not a translation of the original English meaning.
