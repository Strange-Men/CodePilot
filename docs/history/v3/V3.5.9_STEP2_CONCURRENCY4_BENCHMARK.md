### Log Format

All timing logs follow this grep-friendly format:

```
performance_event task_id=<id> stage=<stage> duration_ms=<ms> success=<bool> [retries=<n>] [provider=<name>] [model=<name>] [concurrency=<n>]
```

**No secrets are logged.** Only safe metadata (provider label, model name, retry count) is included.

### Concurrency=4 Verification

The orchestrator already supports `REVIEW_AGENT_CONCURRENCY` via `ThreadPoolExecutor`:

1. **4 agents launch concurrently** — `ThreadPoolExecutor(max_workers=4)` creates 4 threads
2. **Deterministic ordering** — Results are indexed by original position and reassembled in order (A1, A2, A3, A4)
3. **Failure isolation** — `try/except` in `_run_single` catches per-agent exceptions; other agents continue
4. **Progress states valid** — Notifications fire for both success and failure cases
5. **SQLite thread-safe** — `ReviewStore` uses `threading.Lock` for all database operations
6. **Concurrency=1 serial** — `if self.concurrency <= 1: return self._run_serial(state)`
7. **Default remains 2** — `config.py` keeps `review_agent_concurrency` default at 2

### REVIEW_SPEED_MODE Verification

`REVIEW_SPEED_MODE=fast` reduces the per-agent token budget:

```python
if speed_mode == "fast":
    token_budget = max(1000, token_budget // 2)
```

This reduces output tokens but does **not** change the prompt structure or evidence retrieval. The actual latency reduction depends on the LLM provider's output token throughput.

## How to Run Benchmark

### Prerequisites

1. Set API key in `backend/.env`:
   ```
   USE_MOCK_LLM=false
   ENABLE_REAL_LLM=true
   OPENAI_API_KEY=sk-...
   # or
   MIMO_API_KEY=your-key
   ```

2. Install dependencies:
   ```bash
   pip install -r backend/requirements.txt
   ```

### Run with Concurrency=2 (Default)

```bash
python scripts/benchmark_real_review.py --repo-url https://github.com/owner/repo
```

### Run with Concurrency=4

```bash

```

### Run with Fast Speed Mode

```bash
python scripts/benchmark_real_review.py --repo-url https://github.com/owner/repo --concurrency 4 --speed-mode fast
```


### Key Metrics

| Metric | Description |
|--------|-------------|
| `total_pipeline` | End-to-end wall-clock time |
| `clone` | Repository clone time (network dependent) |
| `parse` | Source file parsing time |
| `agent_end` (max) | Slowest agent duration (bottleneck) |
| `report_render` | Report generation time |
| `persistence` | Database write time |
| `retries` | LLM retry count (0 = no retries) |

### Expected Behavior with Concurrency=4

With 4 agents running concurrently:
- `total_pipeline` ≈ `clone` + `parse` + `max(agent_durations)` + `report_render` + `persistence`
- Agent wall-clock ≈ slowest single agent, not sum of all agents
- If all agents take ~2s each, total agent time ≈ 2s (not 8s)

## When to Use Concurrency=2

- **Default production use** — Conservative, lower rate-limit risk
- **Shared API keys** — Reduces concurrent request pressure
- **First-time setup** — Verify everything works before increasing
- **Rate-limited providers** — If you see 429 errors with concurrency=4

## When to Use Concurrency=4

- **Dedicated API keys** — No shared rate limits
- **Benchmarking** — Measure maximum throughput
- **Time-critical reviews** — Need fastest possible turnaround
- **MiMo provider** — Generally supports higher concurrency

## Rate-Limit Warning

If you see these log messages, reduce concurrency:

```
performance_event stage=llm_request success=false provider=... model=... timeout_type=ReadTimeout
performance_event stage=llm_request success=false provider=... model=... error_type=...
```

**Recommendation:**
- 429 errors → Reduce to `REVIEW_AGENT_CONCURRENCY=3` or `2`
- Timeouts → Check network, reduce concurrency
- Consistent failures → Use `USE_MOCK_LLM=true` to verify pipeline

## Step 3 Decision Rule

Based on Step 2 benchmark results:

| Concurrency=4 Result | Recommendation |
|----------------------|----------------|
| ≤ 3 minutes, no rate-limit | Keep 4-agent architecture (current design) |
| 4–6 minutes | Consider 2-call grouped agents (combine related agents) |
| > 6 minutes | Strongly consider single-call multi-agent or Chinese-primary output |
| Rate-limits | Fallback to concurrency=2 or 3, consider 2-call grouped agents |

### Decision Criteria

1. **Wall-clock time** — Measure `total_pipeline` duration
2. **Rate-limit events** — Count `llm_request success=false` with 429 status
3. **Retry rate** — Average `retries` across agents
4. **Agent balance** — Check if one agent is significantly slower (bottleneck)
