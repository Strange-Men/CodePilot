# CodePilot 3.x Master Architecture

> **Note:** This is a historical 3.x planning document written before V3 implementation. The authoritative current V3.1 implementation reference is `docs/V3_ARCHITECTURE.md`.

---

## 1. Executive Summary

CodePilot V2.6 is a repository intelligence engine. It clones public GitHub repositories, parses Python/JavaScript/TypeScript files, builds dependency graphs, constructs structured prompts, and produces four-section review reports through a mock or OpenAI-compatible LLM. The architecture is clean, the contracts are stable, and the test suite is solid at 187+ tests.

**The core problem:** V2.6's final interpretation layer is still mock/template-based. The structural pipeline is strong, but report insight quality is weak. The LLM receives a 5000-token summary prompt with no code evidence, no function signatures, no type information, and no ability to ground its claims in actual source code. The result is generic, surface-level findings that could apply to any repository.

**Recent audits confirmed:**

- V2.6 architecture is complete.
- V2.6 should not continue into V2.7.
- V3 should focus on evidence-grounded real LLM review.
- Replacing mock LLM alone is not enough.
- Context depth is the main bottleneck.
- Agent orchestration should not be introduced before deep context and evidence grounding are proven.

**CodePilot 3.x transforms the system from "Repository Intelligence Engine" into "Evidence-Grounded Multi-Agent Repository Review System."**

The 3.x series spans five versions, each executed as a single Codex Goal with internal phases:

| Version | Codex Goal | Core Outcome |
|---------|-----------|--------------|
| V3.0 | Evidence-Grounded Review MVP | Deep context, evidence store, real LLM, basic agents |
| V3.1 | Graph Orchestration and Structured Storage | Graph-based orchestration, structured finding persistence |
| V3.2 | Retrieval Upgrade and Large Repo Support | Scalable retrieval, context compression, repos above 300 files |
| V3.3 | Developer Workflow Integration | MCP, CLI, CI, PR review modes |
| V3.4 | Evaluation Platform and Production Hardening | Measurable, stable, release-quality |

V3.0 is only the MVP foundation. The full 3.x series is the complete architecture.

## 2. 3.x Architecture Vision

CodePilot 3.x evolves through five distinct stages, each building on the previous one without breaking existing contracts.

**Stage 1 — Deep Context + Evidence Grounding (V3.0):** Extract function signatures, type annotations, class hierarchies, decorators, call relationships, and code snippets from parsed ASTs. Store them as indexed, retrievable evidence. Validate every LLM finding against real evidence before it reaches a report.

**Stage 2 — Graph-Based Agent Orchestration (V3.1):** Replace the simple fan-out/fan-in orchestrator with LangGraph-based conditional routing, checkpoint/resume, and iterative refinement. Persist structured findings and agent intermediate state.

**Stage 3 — Scalable Retrieval (V3.2):** Support repositories above 300 files with tiered retrieval — manifest, symbol, snippet, and optional semantic levels. Add context compression and per-agent retrieval tuning.

**Stage 4 — Developer Workflow Integration (V3.3):** Expose CodePilot through MCP, CLI, CI, and PR review modes. Each integration wraps the existing pipeline; none duplicate review logic.

**Stage 5 — Measurement and Production Quality (V3.4):** Build an evaluation platform that tracks hallucination rates, evidence validity, finding quality, cost, and runtime. Harden for production with cancellation, timeouts, rate limiting, and monitoring.

**The progression is mandatory:** context before agents, single agent before multi-agent, structured output before markdown, evidence before findings. No stage may be skipped.

## 4. 3.x Global Design Principles

These principles govern every version in the 3.x series.

### Principle 1: Evidence First

Every review finding must be grounded in real repository evidence. No evidence, no finding. This is the primary hallucination control mechanism and the foundation of the entire 3.x architecture.

### Principle 2: Sandbox First

All files must pass sandbox filtering before parsing, context building, evidence retrieval, or LLM usage. Safety is not optional and cannot be deferred.

### Principle 3: Context Before Agent

Deep context must be built before real LLM and agent layers. A single agent with deep context outperforms multiple agents with shallow context.

### Principle 4: Single Agent Before Multi-Agent

V3.0 must prove one ArchitectureAgent before expanding to multiple agents. If the single agent produces poor findings, the multi-agent system will amplify the problem.

### Principle 5: Structured Output Before Markdown

LLM output should become structured findings first, then render to the existing Markdown report contract. The LLM never generates the final report directly.

### Principle 6: Mock Mode Must Stay

Mock mode remains default, deterministic, credential-free, and CI-friendly. No version may require API keys for basic operation.

### Principle 7: V2.6 Contracts Must Stay

V3 must preserve: API contract, SQLite compatibility, four-section report contract, frontend behavior, mock mode, parser registry, and ReviewContext compatibility. V3 enriches; it does not break.

### Principle 8: No Framework Tax

Do not add LangChain, LangGraph, vector DB, or heavy RAG frameworks in V3.0 unless clearly justified. V3.0 implements patterns directly. Frameworks enter only when complexity demands them.

### Principle 9: Borrow Patterns, Not Code

Study open-source projects for architecture patterns, but do not copy code unless license compatibility is verified. Every borrowed pattern must be reimplemented in CodePilot's own codebase.

### Principle 10: Codex Goal Mode First

Every 3.x version must be implementable through Codex Goal Mode. Each Goal must be independently shippable, testable, and reversible. Each Goal contains internal phases with strict boundaries, tests, and commits.

## 5. 3.x System Architecture

### Architectural Layers

The 3.x system is organized into seven layers, each with clear responsibilities and dependency rules.

**Layer 1 — API and Task Layer (unchanged from V2.6):**
FastAPI endpoints, task runner, SQLite storage. No contract changes.

**Layer 2 — Safety Layer (V3.0):**
Sandbox filtering, path traversal protection, secret redaction, resource limits. Sits between cloning and parsing. Every file must pass through this layer before any downstream consumer.

**Layer 3 — Deep Context Layer (V3.0):**
Enriched parsing, symbol indexing, call graph construction, class hierarchy extraction, file context generation. Builds the semantic foundation that all agents depend on.

**Layer 4 — Evidence Layer (V3.0):**
Evidence store, evidence retrieval, evidence validation. Generates stable evidence_ids, selects relevant code snippets per review dimension, and validates LLM findings against real evidence.

**Layer 5 — LLM Layer (V3.0):**
Provider-agnostic LLM abstraction, structured output parsing, token budgeting, cost tracking. Supports mock and OpenAI-compatible providers with a protocol-based interface.

**Layer 6 — Agent Layer (V3.0 single agent, V3.0 Phase 3 multi-agent):**
Review agents, orchestrator, finding validator, finding merger. Each agent receives targeted context and evidence bundles, produces structured findings, and validates them against the evidence store.

**Layer 7 — Integration Layer (V3.3):**
MCP server, CLI mode, CI report mode, PR review mode. Each integration wraps the existing pipeline without duplicating review logic.

### Data Flow (V3.0)

The V3.0 review pipeline executes the following steps:

1. Clone the target repository (unchanged from V2.6).
2. Sandbox filter all files — validate paths, enforce limits, apply allowlist, reject symlinks.
3. Redact secrets from file content before any downstream storage or processing.
4. Parse files with enriched parsers — extract signatures, types, decorators, call references.
5. Build deep context — symbol index, file contexts, call graph, class hierarchies.
6. Store evidence — generate stable evidence_ids for all extractable code artifacts.
7. Retrieve evidence per review dimension — select relevant files and code snippets.
8. Run review agent(s) — ArchitectureAgent in Phase 2, four agents in Phase 3.
9. Validate findings — verify evidence_ids, check file existence, verify line ranges, fuzzy-match snippets.
10. Merge and deduplicate findings — remove duplicates, resolve conflicts by confidence.
11. Render report — convert structured findings to four-section Markdown via enhanced MarkdownAdapter.
12. Store and serve — persist in SQLite, serve through existing API contract.

### Data Flow (V3.1+ Evolution)

V3.1 replaces steps 8-10 with LangGraph-based orchestration:

- Each review agent becomes a graph node.
- Conditional routing selects which agents to run based on initial findings.
- Agent intermediate state is persisted for checkpoint/resume.
- Structured findings are persisted alongside the Markdown report.

V3.2 enhances steps 6-7 with tiered retrieval:

- Level 1: Manifest retrieval (file list, roles, scores).
- Level 2: Symbol retrieval (function/class name matching).
- Level 3: Snippet retrieval (relevant code region extraction).
- Level 4: Optional semantic retrieval (embeddings, if justified).

V3.3 adds integration entry points:

- MCP server wraps the pipeline and exposes review as a tool.
- CLI wraps the pipeline and outputs reports to stdout/file.
- CI mode wraps the pipeline and produces non-blocking reports.
- PR mode wraps the pipeline with diff-aware evidence selection.

V3.4 adds evaluation gates:

- Hallucination measurement after every review.
- Golden dataset regression testing.
- Per-agent quality comparison.
- Cost and runtime tracking.

## 7. Evidence ID and Hallucination Control

### Evidence ID Design

The evidence_id system is the foundation of hallucination control. It ensures that every finding can be traced to real repository code.

**Evidence ID Generation:**

The EvidenceStore generates stable evidence_id values during the deep context construction phase. Each evidence_id is a deterministic identifier derived from the file path, line range, and content hash. The same code artifact always produces the same evidence_id across runs.

**Evidence ID Lifecycle:**

1. During deep context construction, the EvidenceStore assigns evidence_ids to all extractable code artifacts: function definitions, class definitions, method definitions, import blocks, route patterns, decorator applications, and call references.
2. Agent prompts provide numbered evidence items, each with an evidence_id, file path, line range, and redacted code snippet.
3. The LLM is instructed to cite evidence_ids in its findings. The LLM does not generate file paths, line ranges, or code snippets directly — it references evidence_ids only.
4. The backend resolves evidence_ids to the actual file path, line range, and redacted code snippet stored in the EvidenceStore.
5. LLM-provided snippets are not trusted as source of truth. The backend always resolves from the EvidenceStore.

**Evidence ID Validation:**

The FindingValidator validates evidence_ids as the first step of finding validation:

1. Check that the evidence_id exists in the EvidenceStore.
2. Check that the referenced file exists in the parsed context.
3. Check that the referenced line range is within the file's bounds.
4. Check that the referenced code snippet matches actual file content (fuzzy match threshold of 0.7).

Findings without valid evidence_ids are rejected immediately. Findings with partially valid evidence_ids have their confidence recalculated based on the ratio of verified evidence.

### Hallucination Control Layers

The system implements five layers of hallucination control:

**Layer 1: Evidence-Grounded Prompts**

Every agent prompt includes explicit evidence with evidence_ids, file paths, line numbers, and redacted code snippets. The prompt instructs the LLM to only report findings it can trace to specific evidence. The prompt explicitly states: do not report findings without specific code evidence, do not invent file names or function names, and if no specific issue can be found, return an empty findings list.

**Layer 2: Structured Output Validation**

The LLM response is parsed into ReviewFinding objects. Pydantic validation enforces: evidence list must have at least 1 entry with a valid evidence_id, confidence must be 0.0-1.0, severity must be a valid enum value. If validation fails, the response is retried once. If it fails again, the agent's findings are discarded.

**Layer 3: Evidence Verification**

The FindingValidator verifies every evidence_id against the EvidenceStore. Findings with no valid evidence are rejected. Confidence is recalculated based on the ratio of verified evidence to total evidence.

**Layer 4: Unsupported Claim Rejection**

Heuristic rejection rules are applied:

- Security injection claims without SQL or query evidence are rejected.
- "Too many responsibilities" claims without listing at least 2 specific responsibilities are rejected.
- "Not tested" claims without referencing a test file gap are rejected.
- Generic findings with low confidence and thin evidence are rejected.

**Layer 5: Confidence Scoring**

Confidence is computed from multiple signals, not just the LLM's self-assessment:

- Evidence quality factor: full score at 2+ evidence references, scaled down for fewer.
- Specificity factor: reduced if file_path is missing or recommendation is missing.
- Severity bar: higher severity findings require higher confidence thresholds.

The final confidence is the product of the base confidence, evidence quality factor, specificity factor, and severity bar, capped at 1.0.

## 8. Sandbox and Tool Safety

### Threat Model

CodePilot analyzes public GitHub repositories — untrusted code. The threats are:

- **Path traversal:** Malicious file paths that resolve outside the repo root.
- **Resource exhaustion:** Repositories with excessive files, large files, or deep directory structures.
- **Secret exposure:** API keys, tokens, passwords in repo files being sent to LLM or stored in reports.
- **Symlink attacks:** Symlinks that point outside the repo root.
- **Code execution:** The architecture must not open doors to eval(), exec(), or subprocess on repo code.

### Sandbox Boundary

The SandboxFilter is the only file entry point. No downstream component may read arbitrary repo files. All file access must go through the sandbox-filtered safe file manifest.

**File Access Rules:**

1. All file paths are resolved relative to the repo root.
2. Paths that resolve outside the repo root are rejected.
3. Symlinks are rejected.
4. File extensions are checked against an allowlist.
5. Path components are checked against a blocked paths set.
6. File size is checked against per-file and total limits.
7. File count is checked against the maximum files limit.

**Resource Limits:**

- Maximum files: 300
- Maximum file size: 200KB per file
- Maximum total size: 50MB
- Maximum lines: 10,000 per file

**Extension Allowlist:**

`.py`, `.js`, `.ts`, `.jsx`, `.tsx`, `.json`, `.md`, `.txt`, `.yml`, `.yaml`, `.toml`

**Blocked Paths:**

`node_modules`, `.git`, `__pycache__`, `.env`, `.venv`, `venv`, `.tox`

### Secret Redaction

The SecretRedactor scans file content for secrets before any content is stored or passed downstream. Detected patterns include:

- API key assignments with string values of 8+ characters
- OpenAI-style keys (sk- prefix)
- GitHub tokens (ghp_ prefix)
- Private key blocks (BEGIN PRIVATE KEY)

Detected secrets are replaced with `[REDACTED: {pattern_name}]`. The redactor returns both the redacted content and a list of detected pattern names.

### Safety Invariants

These invariants are enforced at all times:

1. No file is read outside the cloned repo root.
2. No symlinks are followed.
3. No file exceeding size limits is parsed.
4. No secret is stored in SQLite, sent to LLM, or included in reports.
5. No repo code is executed — parsing is pure analysis.
6. No eval(), exec(), subprocess, or os.system() on repo code.
7. All safety checks happen before content reaches any downstream consumer.
8. Original source content may only be used locally for evidence validation if necessary.
9. Original source content must never be persisted in full or sent to LLM.
10. Path containment is verified through resolved path prefix checking.

## 11. One-Version-One-Goal Strategy

### Why One Goal Per Version

The 3.x architecture uses one Codex Goal per major version, with internal phases carrying strict boundaries, tests, and git commits.

**Too many separate Goals cause:**

- Context fragmentation: each Goal starts fresh without knowledge of prior architectural decisions.
- Architectural drift: independent Goals may introduce inconsistent abstractions.
- Repeated rewrites: modules designed in isolation may conflict when combined.
- Duplicated modules: separate Goals may create overlapping implementations.
- Inconsistent abstractions: naming, patterns, and boundaries diverge across Goals.

**One giant unstructured Goal causes:**

- Token explosion: the Goal prompt exceeds context limits.
- Partial implementation: the Goal is too large to complete in one pass.
- Messy coupling: without phase boundaries, modules blur together.
- Missed tests: without per-phase test requirements, coverage gaps accumulate.

**The solution: one version = one Goal, one Goal = multiple internal phases.**

Each phase within a Goal:

- Has a clear scope and boundary.
- Produces its own tests.
- Produces its own git commit.
- Has its own stop conditions.
- Cannot begin until the previous phase passes its tests.

This structure preserves the context coherence of a single Goal while preventing the chaos of an unstructured mega-implementation. The Codex agent sees the full version scope but executes it in controlled, testable increments.

### Goal Execution Rules

Every Goal must:

1. Inspect the current repository first — read existing files, understand current patterns, adapt to actual code.
2. Preserve existing contracts — API, SQLite, frontend, mock mode, parser registry, ReviewContext.
3. Preserve previous version behavior — V3.1 must not break V3.0; V3.2 must not break V3.1.
4. Avoid rewriting working systems — enhance existing modules; do not replace them without cause.
5. Avoid duplicate modules — one module per responsibility; no parallel implementations of the same concern.
6. Use feature flags for rollout — new behavior is gated; old behavior remains available.
7. Keep CI green — all existing tests pass after every phase.
8. Run tests after every internal phase — no phase commit without passing tests.
9. Commit after every internal phase — each phase produces a clean, independently reviewable commit.
10. Stop if compatibility breaks — any contract violation halts the Goal until fixed.

### Phase Boundary Rules

Each internal phase must:

- Have a defined scope (what is in, what is out).
- Have defined affected modules.
- Have defined acceptance criteria.
- Have defined tests required.
- Have a defined commit name.
- Have defined stop conditions.
- Have a defined "what NOT to do" list.
- Cannot modify modules owned by a later phase unless explicitly stated as a dependency.

### V3.2 Internal Phases

**Phase 1: Tiered Retrieval**

Purpose: Implement four retrieval levels for graduated evidence selection.

Scope:
- Level 1: Manifest retrieval (file list, roles, scores, metadata). Always available.
- Level 2: Symbol retrieval (function/class name matching, import path matching). Builds on V3.0 symbol index.
- Level 3: Snippet retrieval (relevant code region extraction). Builds on V3.0 evidence store.
- Level 4: Optional semantic retrieval. Only introduced if evidence shows Levels 1-3 are insufficient.

Affected Modules:

Purpose: Reduce token usage for large evidence bundles without losing critical information.

Scope:
- Snippet truncation: long code snippets truncated to most relevant region.
- Hierarchical summarization: file-level summaries replace full content when budget is tight.
- Deduplication: duplicate evidence across agents is shared, not repeated.
- Priority-based selection: lowest-ranked evidence dropped first when budget exceeded.

Affected Modules:
- `backend/services/evidence_retriever.py` — Enhanced with compression.

**Phase 3: Large Repo Mode**

Purpose: Handle repositories above 300 files without quality degradation.

Scope:
- File prioritization: only top-N most relevant files fully analyzed.
- Tiered analysis: high-priority files get full deep context; medium-priority get manifest-only; low-priority skipped.

- Configurable thresholds for file count and priority tiers.

Affected Modules:
- `backend/services/evidence_retriever.py` — Enhanced with large repo mode.
- `backend/services/context_engine.py` — Enhanced with tiered analysis.

Scope:
- Evidence recall rate: percentage of findings referencing retrieved evidence.
- Evidence precision rate: percentage of retrieved evidence referenced by findings.
- Retrieval latency: time to retrieve evidence per agent.

Commit: `feat(v3.2): retrieval metrics`

Decision Criteria:
- Evidence recall rate below 70% on representative test set.

CodePilot V3.3: Developer Workflow Integration

### Goal Mission

Move CodePilot from web demo to developer workflow integration. Expose the existing review pipeline through MCP, CLI, CI, and PR review modes without duplicating review logic.

### V3.3 Compatibility Rules

- All V3.0, V3.1, and V3.2 tests must pass.
- Existing API contract is unchanged.
- Existing review pipeline is unchanged.
- All integrations wrap the existing pipeline; none duplicate review logic.
- All integrations support mock mode.

### V3.3 What Must NOT Be Implemented

- Auto-fix or auto-commit
- New review logic
- New agents
- Duplicate review engine
- Frontend changes (integrations are API/CLI/MCP only)

### V3.3 Internal Phases

**Phase 1: MCP Server**

Purpose: Expose CodePilot as a tool that other AI systems can call through the Model Context Protocol.

Scope:
- Single "review_repository" tool accepting a GitHub URL.
- Input schema: repository URL, optional review dimensions, optional file filters.
- Output schema: structured findings (not Markdown), evidence references, quality metrics.
- MCP server calls existing pipeline through the service layer.
- Mock mode support for testing and development.

Affected Modules:
- `mcp/` — New: MCP server implementation.

Commit: `feat(v3.3): mcp server`

Tests: Unit tests for tool definition and schema. Integration test for MCP review invocation.

Stop if: MCP server duplicates review logic. MCP server adds dependencies that break existing tests.

**Phase 2: CLI Mode**

Purpose: Provide command-line access to CodePilot.

Scope:
- Command: `codepilot review <repo_url>` produces Markdown report.
- Output options: stdout, file, JSON.
- CLI calls existing pipeline through service layer.
- CLI does not contain review logic.

Affected Modules:
- `cli/` — New: CLI implementation.

Commit: `feat(v3.3): cli mode`

Tests: Unit tests for CLI argument parsing. Integration test for CLI review invocation.

Stop if: CLI creates a second engine. CLI adds dependencies that break existing tests.

**Phase 3: CI Report Mode**

Purpose: Produce non-blocking reports suitable for CI pipelines.

Scope:
- Command: `codepilot ci <repo_url>` produces CI-compatible report.
- Non-blocking by default: does not fail the build.
- Threshold-based: configurable to fail on findings above severity threshold.
- Exit codes: 0 for success, 1 for failure, 2 for warnings.
- Output: JSON for CI artifact storage, optional Markdown for human reading.

Affected Modules:
- `cli/` — Enhanced with CI mode.

Commit: `feat(v3.3): ci report mode`

Tests: Unit tests for threshold checking. Integration test for CI report generation.

Stop if: CI mode is blocking when configured as non-blocking. CI mode produces different findings than web mode for the same repo.

**Phase 4: PR / Diff Review Mode**

Purpose: Analyze only changed files in a pull request.

Scope:
- Input: GitHub PR URL or diff file.
- Processing: only changed files parsed and analyzed. Evidence retrieval scoped to changed files and direct dependencies.
- Output: findings scoped to diff, with evidence from full repository context.
- PR mode reuses existing pipeline with file filter.

Affected Modules:
- `cli/` — Enhanced with PR mode.
- `backend/tasks/pipeline.py` — Enhanced with file filter support.

Commit: `feat(v3.3): pr diff review mode`

Tests: Unit tests for diff parsing. Integration test for PR-scoped review.

Stop if: PR mode produces findings that differ from full-repo mode for the same files. PR mode breaks existing pipeline behavior.

## 16. V3.4 Goal: Evaluation Platform and Production Hardening

### Goal Name

CodePilot V3.4: Evaluation Platform and Production Hardening

### Goal Mission

Make CodePilot measurable, stable, and release-quality. Build evaluation platform for hallucination regression, finding quality tracking, and agent comparison. Harden for production with cancellation, timeouts, cost caps, and monitoring.

### V3.4 Compatibility Rules

- All V3.0, V3.1, V3.2, and V3.3 tests must pass.
- Existing API contract is unchanged (new fields are optional and additive).
- Existing review behavior is unchanged.
- Production hardening does not change review output.
- Monitoring is optional and non-blocking.

### V3.4 What Must NOT Be Implemented

- Billing
- RBAC
- Team workspace
- Enterprise organization management
- Streaming evaluation
- Real-time monitoring dashboard
- Frontend evaluation dashboard

### V3.4 Internal Phases

**Phase 1: Hallucination Regression Tracking**

Purpose: Track hallucination rates across releases to prevent quality regression.

Scope:
- Evidence validity rate: percentage of findings where all evidence references are valid.
- Invalid evidence rate: percentage of findings with at least one invalid reference.
- Unsupported claim rate: percentage of findings rejected by validation rules.
- Hallucinated file rate: percentage of findings referencing non-existent files.
- Hallucinated line rate: percentage of findings with line ranges outside bounds.
- Regression tracking: compare metrics across releases.

Affected Modules:
- `backend/evaluation/` — Enhanced with hallucination regression tracking.

Commit: `feat(v3.4): hallucination regression tracking`

Tests: Unit tests for each metric. Integration test for regression comparison.

Stop if: Metrics require manual judging for more than 20% of findings. Metrics are flaky in CI.

**Phase 2: Finding Quality Metrics**

Purpose: Track finding quality beyond hallucination — actionability, specificity, severity distribution.

Scope:
- Actionability: percentage of findings with concrete recommendation.
- Specificity: percentage of findings with file_path, line_range, and code snippet.
- Severity distribution: distribution across severity levels.
- Confidence calibration: correlation between confidence and evidence quality.
- Evidence density: average evidence references per finding.
- Duplicate rate: percentage of findings that are duplicates.

Affected Modules:
- `backend/evaluation/` — Enhanced with quality metrics.

Commit: `feat(v3.4): finding quality metrics`

Tests: Unit tests for each metric. Integration test for metric collection during review.

Stop if: Metrics are not measurable. Metrics add significant overhead.

**Phase 3: Agent Quality Metrics**

Purpose: Compare agent performance to identify underperformers and measure unique contributions.

Scope:
- Per-agent hallucination rate.
- Per-agent unique contribution rate.
- Per-agent findings produced.
- Per-agent average confidence.
- Cross-agent coverage analysis.

Affected Modules:
- `backend/evaluation/` — Enhanced with agent quality metrics.

Commit: `feat(v3.4): agent quality metrics`

Tests: Unit tests for per-agent metrics. Integration test for cross-agent comparison.

Stop if: Per-agent metrics are unreliable. Agent comparison produces false conclusions.

**Phase 4: Production Timeouts and Cancellation**

Purpose: Add timeout controls and cancellation support for production reliability.

Scope:
- Per-review timeout (configurable, default 5 minutes).
- Per-agent timeout (configurable, default 2 minutes).
- Per-LLM-call timeout (configurable, default 30 seconds).
- Review cancellation through API.
- Cancellation propagates to all running agents.
- Partial results are not returned on cancellation.

Affected Modules:
- `backend/tasks/runner.py` — Enhanced with timeout and cancellation.
- `backend/api/reviews.py` — Enhanced with cancellation endpoint.

Commit: `feat(v3.4): production timeouts and cancellation`

Tests: Unit tests for timeout enforcement. Integration test for cancellation propagation.

Stop if: Timeouts break existing review behavior. Cancellation leaves orphaned state.

**Phase 5: Cost Caps and Rate Limiting**

Purpose: Control LLM costs and prevent abuse.

Scope:
- Per-review cost cap (configurable).
- Per-day cost cap (configurable).
- Automatic fallback to mock mode when cost cap reached.
- Per-user rate limiting for review submissions.
- Per-IP rate limiting for API access.

Affected Modules:
- `backend/core/config.py` — Enhanced with cost cap and rate limit settings.
- `backend/tasks/runner.py` — Enhanced with cost cap enforcement.
- `backend/api/reviews.py` — Enhanced with rate limiting.

Commit: `feat(v3.4): cost caps and rate limiting`

Tests: Unit tests for cost cap enforcement. Unit tests for rate limiting. Integration test for mock fallback on cost cap.

Stop if: Cost caps are inaccurate by more than 10%. Rate limiting blocks legitimate requests.

**Phase 6: Logs, Traces, and Monitoring**

Purpose: Add structured logging, execution traces, and optional monitoring hooks.

Scope:
- Structured logging for all review operations.
- Per-agent execution traces.
- Token usage and cost traces.
- Health check endpoint (existing, enhanced).
- Optional metrics endpoint (for Prometheus or similar).
- Optional alerting hooks.

Affected Modules:
- `backend/core/logging.py` — Enhanced with structured logging.
- `backend/api/reviews.py` — Enhanced with optional metrics endpoint.

Commit: `feat(v3.4): logs traces and monitoring`

Tests: Unit tests for log format. Integration test for trace collection.

Stop if: Monitoring adds significant overhead to review execution. Logging produces excessive volume.

## 17. Open Source Reference Strategy

### Borrow Patterns, Not Code

These references are for studying patterns and concepts. Do NOT copy code from these projects unless license compatibility is verified. The goal is to understand the design decisions and reimplement the patterns in CodePilot's own codebase.

### Aider

**What to study:** How Aider constructs code context for LLMs (the "repo map" concept), how it selects relevant files using tree-sitter symbols, and how it formats code with line numbers.

**What to borrow:** The concept of a symbol-indexed file ranking system. The pattern of formatting code with file:line references for LLM consumption. The repo map pattern is exactly what CodePilot's EvidenceRetriever needs.

**What to avoid:** Aider's edit format (whole-file or search/replace) — CodePilot is read-only. Aider's dependency on litellm — CodePilot uses a simpler provider abstraction.

### Ruff

**What to study:** Rule-based code analysis patterns. Ruff's visitor pattern (statement/expression node dispatch) is the gold standard for AST-based analysis. Study how rules are structured as composable, testable units.

**What to borrow:** The concept of "fixable" vs "non-fixable" findings for the RefactorAgent. The pattern of composable analysis rules. The AST visitor organization pattern.

**What to avoid:** Reimplementing Ruff's rules — use Ruff as a linter dependency if linting integration is needed. Ruff's Rust implementation — CodePilot stays pure Python.

### Instructor

**What to study:** Structured output from LLMs using Pydantic models. Instructor's approach to retrying on validation errors, patching the OpenAI client, and handling partial responses.

**What to borrow:** The response_model pattern — define a Pydantic model, send it as the expected schema, validate the response, retry on failure. The structured output validation pattern.

**What to avoid:** Adding Instructor as a dependency — implement the pattern directly. Instructor's dependency on pydantic-core internals — use stable Pydantic v2 APIs.

### SWE-bench

**What to study:** Evaluation methodology. SWE-bench's approach to golden datasets, expected outputs, and automated evaluation.

**What to borrow:** The concept of a golden dataset with expected findings and tolerance ranges. The pattern of automated evaluation with structured metrics. The golden dataset methodology.

**What to avoid:** SWE-bench's task format (issue to patch) — CodePilot's evaluation is different (repo to findings). SWE-bench's infrastructure requirements — CodePilot uses pytest + JSON fixtures.

### OpenAI Evals

**What to study:** Evaluation framework patterns — how to define eval tasks, run them against models, and aggregate results.

**What to borrow:** The "custom eval" pattern — define evaluation criteria as structured data, run against model output, aggregate metrics. The custom eval organization pattern.

**What to avoid:** Using the OpenAI Evals framework directly — it is designed for OpenAI models and adds unnecessary dependency. OpenAI Evals' YAML-based eval definition — CodePilot uses JSON fixtures.

### LangGraph

**What to study:** State management patterns, conditional routing concepts, checkpoint/resume patterns. How LangGraph represents agent state and handles errors in multi-step flows.

**What to borrow:** The concept of typed state dicts flowing between nodes. The pattern of conditional edges for routing. The state and routing concepts.

**What to avoid:** Adding LangGraph as a V3.0 dependency. The orchestrator is simple enough to implement directly in V3.0.

### Pyright

**What to study:** Type inference patterns. How Pyright builds a symbol table and resolves types across files.

**What to borrow:** The pattern of extracting type annotations and class hierarchies from ASTs. The concept of a symbol index mapping names to definitions. The symbol table and type annotation extraction patterns.

**What to avoid:** Implementing full type inference — borrow the patterns for extracting what is explicitly annotated, not for inferring what is missing.

### Patterns to Avoid Entirely

- **Do not add LangChain.** Framework tax without proportional value for CodePilot's use case.
- **Do not use Chroma/FAISS for V3.0.** Vector search is overkill for 100-300 files.
- **Do not implement custom AST parsing for JS/TS in V3.0.** Regex is sufficient for V3.0's best-effort enrichment.
- **Do not build a custom evaluation framework.** pytest + JSON fixtures are sufficient.
- **Do not add rank_bm25 unless justified.** Manual BM25 is approximately 80 lines and avoids a dependency.

## 18. 3.x Testing and CI Strategy

### CI Gate (Every Commit)

The following must pass on every commit across all 3.x versions:

- All existing tests (187+ at V3.0 start, growing to 370+ by V3.4).
- Ruff linting with zero warnings.
- Frontend build without TypeScript errors.
- Mock LLM evaluation (deterministic, no API keys).
- Schema validation for all structured output.
- Evidence_id validity for all findings.
- Sandbox tests (path traversal, resource limits, symlinks).

Real LLM evaluation is a manual process, not a CI gate:

- Run on 5 repositories initially.
- Produce hallucination report (evidence validity rate, unsupported claim rate).

- Produce cost report (token usage, estimated cost).

## 19. 3.x Stop Conditions

### V3.0 Stop Conditions

**Phase 1 stop if:**
- Sandbox can be bypassed (any file outside allowlist is read).
- Parser can scan raw repo (any parser reads files directly instead of through safe manifest).
- Evidence_id is unstable (same code artifact produces different evidence_ids across runs).
- Secret appears in evidence or report (any secret passes through redaction).
- V2 parser compatibility breaks (any existing test fails due to parser changes).

**Phase 2 stop if:**
- Mock mode requires API key (mock provider must work without any credentials).
- Structured validation is bypassable (any finding can be produced without passing Pydantic validation).
- Finding can be produced without evidence_id (evidence_id requirement must be enforced).
- LLM failure crashes the whole system (all LLM failures must be caught and handled gracefully).
- Evidence_id resolution returns wrong file or line (resolution must be deterministic and correct).

**Phase 3 stop if:**
- One failed agent kills the whole review (agents must fail independently).
- Dedup removes unrelated findings (dedup_key must be specific enough to avoid false positives).
- Agents bypass evidence_id (all agents must use the same evidence_id validation).
- Four-section report contract changes (the report must maintain the same section structure).
- Agent overlap causes more than 50% duplicate findings (dedup_key tuning is needed).

**Phase 4 stop if:**
- Real LLM eval becomes a required CI gate (it must remain optional).
- Eval is flaky in CI (mock mode must be deterministic).
- Metrics require excessive manual judging (metrics must be automated).
- Golden dataset produces false positives (expected findings must be verified).
- Evaluation cost exceeds budget (cost caps must be enforced).

### V3.1 Stop Conditions

- V3.0 interfaces are broken by V3.1 changes.
- Structured persistence migration breaks existing API responses.
- LangGraph dependency breaks existing tests (if introduced).
- Graph-based orchestration is slower than fan-out/fan-in for parallel agents (if introduced).
- Checkpoint/resume introduces state corruption (if introduced).

### V3.2 Stop Conditions

- Tiered retrieval reduces evidence recall rate below V3.0 levels.
- Context compression loses critical code information.
- Large repo mode produces lower quality findings than standard mode.
- Retrieval quality metrics are not measurable or are flaky.
- Stronger RAG does not improve recall rate (if introduced).

### V3.3 Stop Conditions

- MCP server duplicates review logic instead of wrapping the pipeline.
- CLI creates a second engine instead of wrapping the existing one.
- PR mode produces findings that differ from full-repo mode for the same files.
- CI mode is blocking when configured as non-blocking.
- Any integration breaks existing API behavior.

### V3.4 Stop Conditions

- Evaluation metrics require manual judging for more than 20% of findings.
- Production hardening changes break existing API behavior.
- Monitoring adds significant overhead to review execution.
- Cost tracking is inaccurate by more than 10%.
- Rate limiting blocks legitimate requests.

## 20. 3.x Anti-Scope-Creep Rules

### V3.0 Anti-Scope-Creep

1. **No LangGraph.** The orchestrator is simple fan-out/fan-in. Conditional routing is a V3.1 concern.
2. **No vector DB.** BM25 + graph scoring is sufficient for 100-300 files. Vector search is a V3.2 concern.
3. **No full RAG.** Evidence retrieval is targeted, not semantic. Full RAG is a V3.2 concern.
4. **No Anthropic implementation.** The provider interface supports it, but it is not built.
5. **No MCP.** MCP is a V3.3 concern.
6. **No CLI or CI mode.** CLI and CI are V3.3 concerns.
7. **No PR review.** PR mode is a V3.3 concern.
8. **No SaaS features.** No billing, RBAC, team workspace, or multi-tenancy.
9. **No private repo support.** No OAuth, no token access, no GitHub App.
10. **No breaking API or frontend changes.** All changes are additive and backward-compatible.
11. **No enterprise features.** No custom rules, no reporting dashboard, no team management.
12. **No structured storage migration.** Structured findings are runtime-only in V3.0.

### V3.1 Anti-Scope-Creep

1. **No new agents.** V3.1 restructures orchestration, not agent capabilities.
2. **No new retrieval methods.** V3.1 adds persistence, not retrieval.
3. **No new integrations.** V3.1 is internal architecture, not external integration.
4. **No frontend changes.** Structured data is API-only in V3.1.

### V3.2 Anti-Scope-Creep

1. **No new agents.** V3.2 improves retrieval, not agent capabilities.
2. **No new orchestration.** V3.2 uses V3.1's orchestration.
3. **No new integrations.** V3.2 is retrieval optimization, not external integration.
4. **No enterprise search.** V3.2 is code retrieval, not document search.

### V3.3 Anti-Scope-Creep

1. **No auto-fix.** V3.3 is read-only review integration, not code modification.
2. **No auto-commit.** V3.3 does not write to repositories.
3. **No new review logic.** All integrations wrap the existing pipeline.
4. **No new agents.** V3.3 exposes existing agents through new interfaces.

### V3.4 Anti-Scope-Creep

1. **No billing.** V3.4 tracks costs but does not charge users.
2. **No RBAC.** V3.4 is single-user evaluation, not multi-user management.
3. **No team workspace.** V3.4 is individual evaluation, not team collaboration.
4. **No enterprise organization management.** V3.4 is tool quality, not organizational features.
