# V3.5.12 — Product Usability & UI Polish

> Status: Planning
> Created: 2026-06-17
> Scope: Free-first usability release, no paid infrastructure required.

---

## Executive Summary

V3.5.12 turns the CodePilot prototype into a usable demo product by fixing six concrete usability problems: broken Markdown export, stale local history, non-self-contained exported reports, Chinese language leakage, unclear error messages, and UI polish gaps. All changes work within the free-tier constraint — no paid persistent disk, no Postgres, no external services.

The release has five implementation phases, each independently testable and shippable. Mock mode remains the stable demo path. MiMo remains optional with clear failure messaging. Grouped mode stays experimental and hidden.

---

## Current Product Problems

### P1: Export Navigates to Raw JSON

**Symptom:** Clicking "Export Markdown" opens a new tab that navigates directly to the export URL. If the review no longer exists on the backend (e.g., after Render restart), the browser shows raw JSON error response.

**Root cause:** `ControlSidebar.tsx:128` uses `<a href={getReviewExportUrl(...)}>`, which is a direct link navigation. No fetch, no blob, no error handling.

**Impact:** Broken demo experience. User sees `{"error":"Review not found","code":"review_not_found",...}` in the browser.

### P2: Stale Local History

**Symptom:** After Render redeploy/restart, the backend `/tmp/codepilot.db` is wiped. Frontend still shows old review IDs in history. Clicking a stale review triggers API errors or shows empty state.

**Root cause:** History comes from `GET /api/reviews` which reads from the backend DB. After restart, the DB is empty but the frontend may cache or display stale data from a previous session's `listReviews()` call. No staleness detection exists.

**Impact:** Confusing UX. User clicks a review, gets an error, doesn't understand why.

### P3: Exported Markdown Is Not Self-Contained

**Symptom:** Exported reports reference evidence IDs like `ev_d0b430fe6ccd2d0f552c`. After the backend DB disappears, these IDs are meaningless. The report loses its evidence grounding.

**Root cause:** Evidence display uses internal DB IDs. No user-friendly evidence numbering (E1, E2). No evidence appendix with file, line, symbol, and snippet that would be useful offline.

**Impact:** Exported Markdown degrades in value over time. Not useful as a standalone artifact.

### P4: Chinese Report Quality

**Symptom:** Some MiMo-generated Chinese sections contain English natural language mixed in (e.g., "This function has several issues" inside a Chinese paragraph). Code symbols and file paths should stay English, but surrounding prose should be Chinese.

**Root cause:** MiMo sometimes outputs mixed-language text. No validation or fallback exists for `display.zh` fields.

**Impact:** Unprofessional bilingual output. Chinese readers see jarring language switches.

### P5: Error Visibility

**Symptom:** MiMo provider failures (network timeout, API key invalid, rate limit) look the same as product bugs. All-agent failures show raw error strings. Users can't distinguish "your API key is wrong" from "CodePilot broke."

**Root cause:** Error messages pass through without categorization. No provider/network error detection. No sanitized user-facing messages.

**Impact:** Users blame the product for external provider issues.

### P6: UI Usability Gaps

**Symptom:** The UI is functional but dense. Empty states are generic. Loading states use skeletons without context. Error states are raw text. The report reading experience could be more polished.

**Root cause:** Rapid prototype development prioritized function over form. No design system defined. No consistent status badge system.

**Impact:** First-time users don't understand what to do. Long reports are hard to scan.

## Phase 1 — Export and Stale History

**Goal:** Export never shows raw JSON. Stale history is handled gracefully.

### Backend Changes

None required. The existing `GET /api/reviews/{task_id}/export` endpoint already returns proper `Content-Disposition` headers and JSON error responses.

### Frontend Changes

#### 1a. Export via Fetch + Blob

**File:** `frontend/components/workspace/ControlSidebar.tsx`

Replace the `<a href={...}>` export link with a button that:

1. Calls `fetch(getReviewExportUrl(taskId, { lang }))`.
2. If response is OK: creates a `Blob`, generates an object URL, triggers download via a temporary `<a>` element, revokes the URL.
3. If response is 404: shows a toast/inline message: "This review is no longer available on the server. Please re-run the review."
4. If response is 409: shows "The review must complete before exporting."
5. If other error: shows generic export failure message.

```typescript
async function handleExport(taskId: string, lang: Language) {
  setExporting(true);
  setExportError(null);
  try {
    const response = await fetch(getReviewExportUrl(taskId, { lang }));
    if (!response.ok) {
      if (response.status === 404) {
        setExportError(t(language, "export.reviewNotFound"));
        return;
      }
      const errorData = await response.json().catch(() => null);
      setExportError(errorData?.detail || t(language, "export.failed"));
      return;
    }
    const blob = await response.blob();
    const url = URL.createObjectURL(blob);
    const a = document.createElement("a");
    a.href = url;
    a.download = `codepilot-review-${taskId}${lang === "zh" ? "-zh" : ""}.md`;
    document.body.appendChild(a);
    a.click();
    document.body.removeChild(a);
    URL.revokeObjectURL(url);
  } catch {
    setExportError(t(language, "export.networkError"));
  } finally {
    setExporting(false);
  }
}
```

#### 1b. Stale History Detection

**File:** `frontend/components/workspace/WorkspaceShell.tsx`

When `selectHistoricalReview` is called and the review data comes from the local `history` array (which was fetched from the backend), the review object is already available — no extra API call needed. The staleness issue occurs when:

1. The backend restarts (DB wiped).
2. The frontend calls `listReviews()` — returns empty array.
3. History is already empty from the backend perspective.

So the main issue is: the frontend should not cache history across page reloads. The current implementation already fetches fresh history on mount (`useEffect` → `refreshHistory()`). The staleness problem is minimal with the current architecture.

**Additional safeguard:** When a user selects a review from history and the subsequent `getReview()` call returns 404, show a clear message:

```typescript
// In WorkspaceShell, when getReview fails for a historical review:
if (error.code === "review_not_found") {
  // Remove from local history
  setHistory((current) => current.filter((item) => item.task_id !== failedTaskId));
  setError(t(language, "error.reviewNoLongerAvailable"));
}
```

#### 1c. i18n Additions

**File:** `frontend/lib/i18n.ts`

Add keys:

```

"export.failed": "Export failed. Please try again."
"export.networkError": "Network error during export. Please check your connection."
```

## Phase 2 — Self-Contained Markdown Evidence

**Goal:** Exported Markdown is readable and useful after backend DB disappears.

### Backend Changes

#### 2a. Evidence ID Mapping

**File:** `backend/reviewers/` (export/render logic)

When generating the Markdown report for export, map internal evidence IDs to sequential display IDs:

- `ev_d0b430fe6ccd2d0f552c` → `E1`
- `ev_a1b2c3d4e5f6...` → `E2`
- etc.

The mapping should be deterministic (sorted by first appearance in the report).

Implementation approach:

1. Collect all unique `ev_*` IDs from findings' `evidence_ids` fields.
2. Sort by first appearance order in the findings list.
3. Create a mapping `{ ev_id → E{n} }`.
4. Replace all `ev_*` references in the report body with `E{n}`.
5. Append an evidence appendix at the end of the report.

#### 2b. Evidence Appendix

Append a new section to the exported Markdown:

```markdown
## Evidence Appendix

| ID | File | Lines | Symbol | Type | Summary |
|----|------|-------|--------|------|---------|
| E1 | `backend/api/reviews.py` | 42–58 | `export_review` | function_definition | The export endpoint returns raw JSON without content negotiation |
| E2 | `backend/storage/sqlite.py` | 112–130 | `get_review` | function_definition | SQLite query uses task_id as primary key lookup |
```

Fields:

- **ID**: Sequential display ID (E1, E2, ...).
- **File**: Relative file path from the repository.
- **Lines**: Start–end line range.
- **Symbol**: Function/class/method name if available.
- **Type**: Evidence type (function_definition, class_definition, etc.).
- **Summary**: One-line description of what this evidence shows.

If evidence metadata is incomplete (e.g., no symbol name), show "—" for that field.

#### 2c. Evidence in Findings

Each finding that references evidence should show `[E1]` inline:

```markdown
### Finding: Unhandled exception in export endpoint

**Severity:** High
**Evidence:** [E1](#evidence-appendix), [E2](#evidence-appendix)

The export endpoint at `backend/api/reviews.py:42` does not handle...
```

### Frontend Changes

#### 2d. Evidence Panel Update

**File:** `frontend/components/workspace/EvidencePanel.tsx`

Update the evidence panel to show E1/E2 style IDs alongside or instead of raw `ev_*` IDs. The mapping should be computed client-side from the findings data (same algorithm as backend).

#### 2e. Report Evidence Links

**File:** `frontend/components/ReportRenderer.tsx` or `MarkdownContent.tsx`

Make `[E1]` references in the rendered report clickable, scrolling to the evidence appendix or opening the evidence panel.

## Phase 3 — Chinese Quality Guard

**Goal:** Chinese reports do not contain obvious English natural-language leakage.

### Backend Changes

#### 3a. Zh Output Validator

**File:** New utility in `backend/reviewers/` or `backend/prompts/`

Create a function `detect_english_leakage(text: str) -> list[str]` that:

1. Tokenizes the text into sentences/segments.
2. Identifies segments that are primarily English natural language (not code, paths, or commands).
3. Returns a list of problematic segments.

Detection heuristic:

- A segment is "English natural language" if:
  - It contains 3+ consecutive English words.
  - It is NOT inside backticks (code), NOT a file path, NOT a URL, NOT a command.
  - It is NOT a known technical term whitelist (e.g., "API", "HTTP", "SQL", "JSON").
- A segment is "acceptable English" if:
  - It is a code symbol (`function_name`, `ClassName`).
  - It is a file path (`backend/api/reviews.py`).
  - It is a command (`pip install`, `npm run build`).
  - It is a technical acronym (API, HTTP, SQL, JSON, LLM, etc.).

#### 3b. Renderer Fallback

**File:** Backend export/render logic

When rendering a Chinese report:

1. Run `detect_english_leakage()` on each `display.zh` field.
2. If leakage is detected in a finding's zh title or description:
   - Log a warning.
   - Fall back to the English field with a `[EN]` prefix.
   - Do NOT silently replace — the user should know the zh translation was imperfect.
3. For the report body, apply the same check and fallback.

This is a **graceful degradation**, not a hard error. The report still exports, but with clear indication that some sections are English fallback.

#### 3c. Technical Term Whitelist

Maintain a list of English terms that are acceptable in Chinese text:

```
API, HTTP, HTTPS, SQL, JSON, YAML, CSV, XML, HTML, CSS, JS, TS, PR, MR, CI, CD,
LLM, AI, ML, NLP, SDK, CLI, GUI, UI, UX, ORM, OOP, FP, AST, CFG, DFG,
Python, JavaScript, TypeScript, Go, Rust, Java, C++, Ruby, PHP, Swift, Kotlin,
Git, GitHub, GitLab, Docker, Kubernetes, K8s, Terraform, AWS, GCP, Azure,
FastAPI, Flask, Django, Express, React, Vue, Angular, Next.js, Svelte,
pytest, jest, mocha, ruff, eslint, prettier, mypy, pyright,
SQLite, PostgreSQL, MySQL, Redis, MongoDB, Elasticsearch,
function, class, method, variable, parameter, argument, return, import, export,
async, await, try, catch, throw, raise, yield, lambda, decorator, mixin,
interface, type, enum, struct, trait, impl, module, package, namespace,
TODO, FIXME, HACK, NOTE, WARNING, DEPRECATED
```

## Phase 4 — UI Usability Polish

**Goal:** UI looks more polished but remains fast and readable. Apply DESIGN.md.

### 4a. Error State Improvements

**Files:** `ControlSidebar.tsx`, `WorkspaceShell.tsx`

Categorize errors into user-facing types:

| Error Type | Message | Icon |
|-----------|---------|------|
| Provider auth | "MiMo API key is invalid or missing. Check backend configuration." | Key icon |
| Provider network | "Cannot reach MiMo provider. The service may be temporarily unavailable." | Wifi-off icon |
| Provider rate limit | "MiMo rate limit reached. Please wait a moment and try again." | Clock icon |
| Review not found | "This review is no longer available. It may have been cleared after a server restart." | Alert icon |
| Generic | "Something went wrong. Please try again." | Alert icon |

Detection heuristic (frontend, from error message/code):

```typescript
function categorizeError(error: string, code?: string): ErrorCategory {
  if (code === "review_not_found") return "review_not_found";
  if (error.includes("API key") || error.includes("401") || error.includes("Unauthorized")) return "provider_auth";
  if (error.includes("timeout") || error.includes("ECONNREFUSED") || error.includes("network")) return "provider_network";
  if (error.includes("429") || error.includes("rate limit")) return "provider_rate_limit";
  return "generic";
}
```

## Recommendation

**Proceed to implementation.** The five phases are independently scoped, each touches a bounded set of files, and none require architectural changes. The plan is executable in 5–8 Goal Mode sessions.

If time is constrained, **Phases 1 and 2** deliver the highest user-facing value (working export + self-contained reports). Phase 3 (zh quality) is important for Chinese demo. Phase 4 (UI polish) is the lowest risk and can be done incrementally.

Do NOT attempt all phases in a single session. Each phase should be committed and tested independently.
