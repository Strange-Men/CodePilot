## 4. Parser Defensive Fixes

### Problem

The Step 3 benchmark reported `"list indices must be integers or slices, not str"`
in both modes. This indicates the LLM returned unexpected JSON structure (e.g., a
list where a dict was expected), and the parser did not handle it gracefully.

### Fixes Applied (`backend/llm/structured.py`)

| Location | Fix |
|---|---|
| `_parse_findings` (separate) | Top-level JSON that is not dict or list now raises `ValueError` with clear message instead of silently treating a string/number as findings. |
| `_parse_findings` (separate) | `no_findings_reason` non-string values are sanitized to `None`. |
| `_parse_findings` (separate) | `findings` value that is not a list now raises `ValueError` instead of crashing on iteration. |
| `_parse_grouped_response` (grouped) | `no_findings_reason` non-string values are now sanitized to `None` (was missing; mock path had this check but real-LLM path did not). |
| `_parse_grouped_response` (grouped) | `findings` value that is not a list now produces a per-agent `parse_error` instead of crashing. Valid siblings are salvaged. |

### Tests Added

10 new tests in `tests/unit/test_grouped_mode.py`:

| Test | What It Verifies |
|---|---|
| `test_grouped_parser_rejects_top_level_list` | JSON list at top level raises ValueError |
| `test_grouped_parser_rejects_agent_outputs_as_list` | agent_outputs as list raises ValueError |
| `test_grouped_parser_handles_findings_as_dict` | findings=dict produces per-agent parse_error |
| `test_grouped_parser_handles_findings_as_string` | findings=string produces per-agent parse_error |
| `test_salvage_valid_sibling_when_findings_wrong_type` | Valid agent salvaged when sibling has wrong-type findings |
| `test_grouped_no_findings_reason_non_string_sanitized` | Non-string no_findings_reason → None |
| `test_separate_parser_rejects_top_level_string` | Separate parser rejects JSON string |
| `test_separate_parser_rejects_top_level_number` | Separate parser rejects JSON number |
| `test_separate_parser_rejects_findings_as_non_list` | Separate parser rejects non-list findings |
| `test_separate_no_findings_reason_non_string_sanitized` | Separate parser sanitizes non-string no_findings_reason |

## 5. Chinese Report Label Mismatch: False Positive

### What the Benchmark Reported

Step 3 benchmark showed "Chinese report-level labels missing in both modes"
and "English leakage terms found in both modes."

### Root Cause

The benchmark script (`scripts/benchmark_real_review.py`) does **NOT** validate
Chinese labels. It is a pure timing benchmark. The "Chinese readiness" check in
Step 3 was done by inspecting DB content (raw structured findings stored before
report rendering), not by calling the `/export?lang=zh` API endpoint.

The raw DB content always stores English text because the zh rendering pipeline
is a post-processing step applied at API response time. This is by design:
the pipeline follows a "compose-in-English-then-translate" architecture.

### Evidence That zh Rendering Works

`tests/unit/test_zh_report_quality.py` contains 31 tests that verify the full
zh rendering pipeline:

- `# 优先处理建议` heading appears in zh reports
- All 6 banned English labels (`Recommendation:`, `Impact:`, `First step:`,
  `Validation tests:`, `Category:`, `Grounding:`) are translated to Chinese
- All 10 required Chinese labels (`建议：`, `影响：`, `建议先做：`, `验证方式：`,
  `注意事项：`, `证据说明：`, `问题类型：`, `涉及文件：`, `证据引用：`, `置信度：`) are present
- Priority section ordering is correct (执行摘要 < 优先处理建议 < 仓库概览)
- Bilingual report with prose replacement works
- Default section content is translated

All 31 tests pass.

### Verdict

**False positive.** The benchmark QA check was reading the wrong content (DB
instead of rendered report). No code fix needed for zh rendering. The Step 3
benchmark doc has been annotated with this resolution.

## 9. Recommendation

**Stop V3.5.10 here as experimental grouped mode.**

Rationale:
1. Separate mode is stable and produces findings.
2. Grouped mode failed its first benchmark — 3x slower, 0 findings.
3. Parser is now defensively hardened against unexpected JSON shapes.
4. Chinese report rendering is confirmed working (false positive resolved).
5. Further grouped optimization (prompt size, streaming, fallback) is a
   separate effort that should not block V3.5.10 closure.

**Next step options:**
- **Option A:** Release V3.5.10 as a stabilization release (experimental grouped flag + parser fixes + docs).
- **Option B:** Continue V3.5.10 with grouped prompt reduction work (not recommended — large effort, uncertain outcome).
