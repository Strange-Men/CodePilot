# V3.5.10 Step 1 — Grouped Agents Design

> Status: Design only — no code changes in this step.
> Created: 2026-06-16
> Baseline: V3.5.9 stable release

## 1. Executive Summary

V3.5.10 should implement a 2-call grouped agent mode behind a feature flag (`REVIEW_AGENT_MODE=grouped`). The current V3.5.9 architecture uses 4 independent LLM calls — one per agent — which dominates wall-clock latency. Grouping logical agents into 2 physical LLM calls can reduce latency by roughly 50% while preserving the 4-agent report identity, evidence grounding, bilingual display, and validation rigor.

**Recommendation:** Proceed with implementation behind an opt-in flag. Keep `separate` as default until a real MiMo benchmark proves grouped mode is faster without quality regression.

## 3. Current 4-Agent Flow

### 3.1 Agent Classes

All four agents extend `EvidenceGroundedAgent` (`backend/agents/evidence_agent.py`):

| Agent | Role | Section | Category | Evidence Query | Limit |
|-------|------|---------|----------|---------------|-------|
| `ArchitectureAgent` | `ArchitectureAgent` | Architecture Summary | `architecture` | architecture entry point core module dependency route class function | 10 |
| `CodeSmellAgent` | `CodeSmellAgent` | Code Smells | `code_smell` | complexity duplicate long function too many calls code smell hotspot | 8 |
| `MaintainabilityAgent` | `MaintainabilityAgent` | Maintainability Issues | `maintainability` | maintainability dependency fan in fan out orphan hub tests boundary | 8 |
| `RefactorAgent` | `RefactorAgent` | Refactoring Suggestions | `refactor` | refactor extraction boundary interface split simplify dependency | 8 |

### 3.2 Instantiation

In `AgentOrchestrator.run()` (`backend/agents/orchestrator.py`), each agent class is instantiated with:
- `llm_client` (shared)
- `model` (shared)
- `token_budget` (per-agent, `per_agent_token_budget`)

Each agent gets its own `StructuredLLMClient` wrapper and `CostTracker`.

### 3.3 Evidence and Context

Each agent calls `EvidenceRetriever.retrieve_with_policy()` with its own `RetrievalPolicy`:
- `agent_role` — the agent's role string
- `query` — the agent's `evidence_query`
- `limit` — the agent's `evidence_limit`
- `token_budget` — shared per-agent budget

Evidence is agent-specific: different queries produce different evidence bundles from the same `ReviewContext.evidence` pool.

### 3.4 LLM Call

Each agent calls `StructuredLLMClient.generate_findings()` once:
1. Renders a prompt with evidence snippets, schema guidance, and bilingual display rules.
2. Calls `llm_client.generate_review(prompt)`.
3. Parses JSON response into `RawLLMFinding` list.
4. Filters findings to only include allowed `evidence_ids`.
5. Retries once on parse failure.

### 3.5 Validation

`FindingValidator.validate()` (`backend/agents/finding_validator.py`) runs per finding:
- Checks section is in `REPORT_SECTIONS`.
- Resolves each `evidence_id` against `EvidenceStore`.
- Rejects findings with hallucinated or missing evidence IDs.
- Preserves medium/low severity findings.
- Maps `RawLLMFinding` → `ReviewFinding` with resolved `files` and `evidence` grounding.

### 3.6 State Persistence

Each agent produces an `AgentExecutionState` with:
- `agent_id` — the agent's role string
- `status` — "completed" or "failed"
- `findings` — validated `ReviewFinding` list
- `evidence_ids` — evidence IDs from the bundle
- `prompt_tokens`, `completion_tokens`, `llm_calls` — cost metadata
- `validation_status` — "validated" or "failed"
- `metadata` — duration, retrieval stats, `no_findings_reason`

States are persisted per-agent in `review_agent_states` table.

### 3.7 Report Mapping

`HumanReadableReportComposer` (`backend/reviewers/report_composer.py`) maps findings to sections via `finding.section`. The `_agent_summary()` and `_agent_findings()` methods iterate `agent_states` to produce per-agent tables. The `_contract_sections()` method groups findings by the 4 report section titles from `contracts/report_sections.json`.

## 4. Why Grouped Agents Are Being Considered

### Latency Problem

Current V3.5.9 makes 4 physical LLM calls. Even with `concurrency=4`, wall-clock time is bounded by the slowest call. Real MiMo latency varies:
- Best case: ~121s total
- Typical: ~280s
- Each agent call: ~30–80s depending on provider load

Reducing from 4 calls to 2 calls can:
- Cut LLM-bound latency by up to 50% (2 slowest calls instead of 4)
- Reduce cost by combining prompts (fewer total tokens across calls)
- Improve stability (fewer independent failure points)

### Why Not Single Call

A single call producing all 4 agents' findings would:
- Create a very large prompt (4× evidence, 4× schema guidance)
- Create a very large output schema (4× findings)
- Increase parse failure risk dramatically
- Lose all failure isolation

The 2-call grouped approach is a middle ground: meaningful latency reduction with manageable complexity.

## 5. Proposed 2-Call Grouped Flow

### Grouping

| Group | Logical Agents | Rationale |
|-------|---------------|-----------|
| Group 1 | ArchitectureAgent + MaintainabilityAgent | Both analyze structural properties: architecture focuses on entry points, modules, dependencies; maintainability focuses on fan-in/out, orphans, hubs. Evidence queries overlap on dependency/graph concepts. |
| Group 2 | CodeSmellAgent + RefactorAgent | Both analyze code-level quality: code smells detect patterns; refactor suggests improvements. Evidence queries overlap on complexity, duplication, extraction. |

### Flow

```
Group 1 call:
  1. Retrieve evidence for ArchitectureAgent and MaintainabilityAgent (separately)
  2. Render combined prompt with both agents' evidence and schema
  3. Single LLM call
  4. Parse grouped response
  5. Split into ArchitectureAgent and MaintainabilityAgent logical outputs
  6. Validate each logical agent's findings independently
  7. Build separate AgentExecutionState for each

Group 2 call (runs concurrently with Group 1):
  1. Same pattern for CodeSmellAgent + RefactorAgent
```

Both groups run concurrently (2 physical calls instead of 4), reducing wall-clock to the slower group's duration.

### Evidence Handling

Each logical agent still retrieves its own evidence bundle independently before the grouped call. The combined prompt includes both agents' evidence sections, clearly labeled. The LLM must assign findings to the correct logical agent via the `agent_outputs` wrapper.

## 6. Proposed Grouped Output Schema

### Group 1 Response Shape

```json
{
  "agent_outputs": {
    "ArchitectureAgent": {
      "findings": [
        {
          "title": "string",
          "description": "string",
          "category": "architecture",
          "severity": "high|medium|low",
          "confidence": 0.0-1.0,
          "evidence_ids": ["ev_abc123"],
          "recommendation": "string|null",
          "impact": "string|null",
          "first_step": "string|null",
          "validation_tests": ["string"],
          "confidence_rationale": "string|null",
          "caveat": "string|null",
          "display": {
            "en": {"title": "...", "description": "...", ...},
            "zh": {"title": "...", "description": "...", ...}
          }
        }
      ],
      "no_findings_reason": null
    },
    "MaintainabilityAgent": {
      "findings": [],
      "no_findings_reason": "Evidence shows no maintainability issues."
    }
  }
}
```

### Group 2 Response Shape

```json
{
  "agent_outputs": {
    "CodeSmellAgent": {
      "findings": [...],
      "no_findings_reason": null
    },
    "RefactorAgent": {
      "findings": [...],
      "no_findings_reason": null
    }
  }
}
```

### Finding Fields Preserved

Every finding in the grouped output keeps all existing fields:
- `title`, `description` — core finding text
- `category` — must match the logical agent's category
- `severity` — high/medium/low
- `confidence` — 0.0–1.0
- `evidence_ids` — must reference evidence from the correct agent's bundle
- `recommendation`, `impact`, `first_step` — actionable guidance
- `validation_tests` — test commands or files
- `confidence_rationale`, `caveat` — quality metadata
- `display.en`, `display.zh` — bilingual display fields

### Parser Changes Required

`StructuredLLMClient` needs a new method `generate_grouped_findings()` that:
1. Parses the top-level `agent_outputs` object.
2. Iterates logical agent keys.
3. For each logical agent, parses its `findings` array as `RawLLMFinding` list.
4. Returns a `GroupedStructuredLLMResult` with per-agent findings and `no_findings_reason`.

## 7. Preserving 4 Logical Agent Identities

| Aspect | Separate Mode | Grouped Mode |
|--------|--------------|--------------|
| Physical LLM calls | 4 | 2 |
| Logical agent records | 4 | 4 |
| `AgentExecutionState` entries | 4 | 4 |
| Report sections | 4 | 4 |
| Agent summary table | 4 rows | 4 rows |
| Agent findings sections | 4 | 4 |
| Frontend agent display | Unchanged | Unchanged |
| Storage schema | Unchanged | Unchanged |

The grouped mode changes only the physical call pattern. The logical identity — agent IDs, report sections, per-agent state — remains identical. The frontend, API, and storage layers see no difference.

## 8. Failure and Retry Strategy

### 8.1 Group Independence

- If Group 1 fails, Group 2 still runs.
- If Group 2 fails, Group 1's results are still valid.
- Both groups are independent; neither blocks the other.

### 8.2 Partial Salvage

If a grouped response contains one valid logical agent output and one invalid:
- **Salvage the valid output.** Parse and validate it normally.
- **Record the invalid output as failed** with appropriate error in `AgentExecutionState`.
- **Do not retry the entire group** if one part succeeded. Only retry the failed logical agent by running it as a separate fallback call.

Salvage criteria:
- The `agent_outputs` top-level object parsed successfully.
- One logical agent key's `findings` array parsed and validated.
- The other logical agent key is missing, malformed, or contains invalid findings.

### 8.3 Retry Policy

- **Group-level retry:** If the entire grouped response fails to parse (invalid JSON, missing `agent_outputs`), retry the group once.
- **Logical-agent fallback:** If one logical agent's output is invalid after salvage, run that agent as a separate `EvidenceGroundedAgent.review()` call (same as V3.5.9 separate mode).
- **Max retries:** 1 group-level retry + 1 fallback separate call per failed logical agent.

### 8.4 Failure Isolation

- Each logical agent's `AgentExecutionState` is built independently.
- One logical agent's failure does not affect the other's state.
- `no_findings_reason` is recorded per logical agent.
- Error messages are per logical agent.

## 9. Validation Strategy

### 9.1 Parse Flow

1. Receive grouped JSON response.
2. Parse top-level `agent_outputs` object.
3. For each logical agent key (e.g., `ArchitectureAgent`):
   a. Extract `findings` array and `no_findings_reason`.
   b. Parse each finding as `RawLLMFinding`.
   c. Filter to allowed `evidence_ids` for that agent's bundle.
4. Run `FindingValidator.validate()` per finding, with the agent's `section`.
5. Build `AgentExecutionState` per logical agent.

### 9.2 Evidence Grounding

- Each logical agent's findings are validated against its own evidence bundle.
- Evidence IDs from Group 1's ArchitectureAgent findings must resolve in ArchitectureAgent's bundle.
- Cross-contamination (ArchitectureAgent citing MaintainabilityAgent's evidence) is filtered by `_filter_allowed()`.

### 9.3 Bilingual Display

- `display.en` and `display.zh` fields are preserved unchanged through validation.
- `FindingValidator` already preserves `display` on the `ReviewFinding` it produces.

### 9.4 Severity Preservation

- Medium and low findings are preserved (V3.5.9 behavior).
- No severity filtering beyond evidence grounding.

## 10. Timing and Logging Strategy

### New Log Stages

| Stage | When | Fields |
|-------|------|--------|
| `grouped_call_start` | Before grouped LLM call | `task_id`, `group_id`, `logical_agents`, `concurrency` |
| `grouped_call_end` | After grouped LLM call | `task_id`, `group_id`, `duration_ms`, `success`, `retries`, `provider`, `model` |
| `logical_agent_parse` | After parsing each logical agent | `task_id`, `agent_id`, `raw_finding_count`, `parse_success`, `error` |
| `logical_agent_validation` | After validating each logical agent | `task_id`, `agent_id`, `validated_count`, `dropped_count`, `no_findings_reason` |
| `grouped_retry` | On group-level retry | `task_id`, `group_id`, `attempt`, `error_type` |
| `logical_agent_fallback` | On fallback to separate call | `task_id`, `agent_id`, `reason` |

### Duration Attribution

- `group_call_duration_ms` — time for the physical LLM call (group-level).
- `logical_agent_duration_ms` — time for parse + validation of one logical agent (includes evidence retrieval time recorded separately).
- `AgentExecutionState.metadata["group_id"]` — which group this agent belonged to.
- `AgentExecutionState.metadata["call_mode"]` — "grouped" or "separate" (for fallback).

## 11. Feature Flag Plan

### Environment Variable

```
REVIEW_AGENT_MODE=separate|grouped
```

### Behavior

| Value | Behavior |
|-------|----------|
| `separate` (default) | V3.5.9 behavior: 4 independent agents, 4 LLM calls. No change. |
| `grouped` | V3.5.10 grouped mode: 2 grouped calls, 4 logical agent outputs. |

### Implementation

- Add `review_agent_mode` field to `Settings` (`backend/core/config.py`).
- `AgentOrchestrator` checks mode and dispatches to `_run_separate()` or `_run_grouped()`.
- `_run_grouped()` implements the 2-call grouped flow.
- `_run_separate()` is the existing `_run_serial()` / `_run_parallel()` path.

### Rollout

1. Implement grouped mode behind flag. Default: `separate`.
2. Run benchmark with `grouped` mode on same repo/model.
3. If quality and latency are acceptable, consider making `grouped` default.
4. Never remove `separate` mode — it remains as fallback.

## 13. Architecture Options Comparison

### Option A: Keep V3.5.9 4-Agent Separate Mode

| Aspect | Assessment |
|--------|-----------|
| Pros | Zero implementation risk. Proven behavior. All tests pass. |
| Cons | No latency improvement. 4 LLM calls remain the bottleneck. |
| Quality risk | None — behavior is unchanged. |
| Latency | Same as V3.5.9: ~121s best, ~280s typical. |
| Implementation risk | None. |

### Option B: 2-Call Grouped Agents (Recommended)

| Aspect | Assessment |
|--------|-----------|
| Pros | ~50% fewer LLM calls. Preserves 4 logical agents. Feature-flagged. |
| Cons | More complex parser. Salvage logic needed. Larger prompts. |
| Quality risk | Medium — larger prompt may reduce per-finding quality. Must benchmark. |
| Latency | Expected ~60–150s (2 slowest calls instead of 4). |
| Implementation risk | Medium — new parser, new orchestrator path, new tests. |

### Option C: Single-Call Multi-Agent

| Aspect | Assessment |
|--------|-----------|
| Pros | Only 1 LLM call. Maximum latency reduction. |
| Cons | Very large prompt. Very complex output schema. No failure isolation. Single point of failure. |
| Quality risk | High — LLM must handle 4× evidence and 4× schema in one response. |
| Latency | Expected ~30–80s (single call). |
| Implementation risk | High — schema complexity, parse reliability, no salvage possible. |

### Recommendation

**Option B** is the best balance. It provides meaningful latency reduction (~50%) with manageable complexity. Option C is too risky for quality; Option A provides no improvement.

## 15. Benchmark Plan

### Setup

- Same repository (e.g., CodePilot itself or a public fixture).
- Same MiMo model (`mimo-v2.5-pro`).
- Same `REVIEW_AGENT_CONCURRENCY=2`.

### Runs

| Run | Mode | Metrics Collected |
|-----|------|-------------------|
| Baseline | `REVIEW_AGENT_MODE=separate` | `total_pipeline`, per-agent `duration_ms`, finding count, Chinese quality |
| Grouped | `REVIEW_AGENT_MODE=grouped` | `total_pipeline`, per-group `duration_ms`, per-agent finding count, Chinese quality |

### Comparison

- Total pipeline duration: grouped should be lower.
- Finding count: grouped should be comparable (±20%).
- Chinese quality: grouped should match separate (same bilingual prompt rules).
- Evidence grounding: grouped should have zero hallucinated evidence.

### Decision Criteria

- If grouped is ≥30% faster with comparable quality → make grouped the default.
- If grouped is <30% faster or quality drops → keep separate as default.
- If grouped fails frequently → investigate prompt/schema before proceeding.

## 16. Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| Larger prompt reduces LLM reliability | Medium | High | Benchmark quality; fallback to separate on failure. |
| One grouped call failure affects 2 agents | Low | Medium | Salvage valid output; fallback to separate for failed agent. |
| Schema complexity increases parse failures | Medium | Medium | Robust parser with code-fence stripping; retry once. |
| Quality drops for individual findings | Low | Medium | Validate per-agent; compare finding counts in benchmark. |
| Salvage logic introduces bugs | Medium | Low | Comprehensive unit tests for salvage paths. |
| Feature flag adds config surface | Low | Low | Document in `.env.example`; default is safe (`separate`). |

## 17. Recommendation for Step 2

**Proceed** with grouped mode implementation behind `REVIEW_AGENT_MODE=grouped`.

### Step 2 Scope

1. Add `review_agent_mode` to `Settings` (`backend/core/config.py`).
2. Add `GroupedStructuredLLMResult` and `generate_grouped_findings()` to `backend/llm/structured.py`.
3. Add `_run_grouped()` to `AgentOrchestrator` with grouped call, parse, salvage, and fallback logic.
4. Add grouped prompt rendering to `EvidenceGroundedAgent` (new `_render_grouped_prompt()` method).
5. Add timing/logging for grouped stages.
6. Add unit tests for grouped schema parsing, validation, salvage, fallback, and flag behavior.
7. Run benchmark comparing `separate` vs `grouped` on same repo/model.
8. Document results and decide on default.

### Not in Step 2

- No database migration.
- No frontend changes.
- No API changes.
- No report composer changes.
- No default behavior change (default remains `separate`).
